# 定义目标

## 概述

将用户的意图塑造成一个代理可以诚实追求的目标。优先选择可衡量的结果、明确的证据和有边界的范围，而不是活动性的描述。

此技能仅涵盖目标的定义和goal工具的创建。不要在此技能中创建中间规划产物、持久化快照、账本、决策日志或恢复文件。

## 工作流程

1. 确认确实需要定义目标。
   - 当用户要求 `$define-goal`、要求创建或设定一个目标、要求使用goal工具，或希望帮助将一个意图转化为一个清晰的目标时，使用此技能。
   - 如果用户只是要求普通的实现工作，请直接完成这项工作，而不要强行创建目标。

2. 用具体的措辞重新陈述可能的目标。
   一个可用的目标需要指明：
   - 将会成立的具体结果
   - 涉及的主要产物、系统、仓库、环境或面向用户的行为
   - 完成情况将如何被验证
   - 范围内包含什么
   - 当歧义会造成影响时，范围外排除什么
   - 应该停下来询问用户而不是硬撑下去的停止条件

3. 当领域支持时，使其量化。
   优先使用代表真实成功的数字，而不是装饰性的精确度：
   - 通过/失败验证器：确切的测试、检查、CI作业、评测（evals）、命令或验收标准
   - 质量门限：延迟、错误率、成本、准确率、召回率、精确率、覆盖率、不稳定率（flake rate）、打包体积、内存、正常运行时间、完成率，或人工审查标准
   - 产物约束：文件路径、受影响的模块、允许的命令、输出格式、目标环境、截止日期，或最大影响范围
   - 证据数量：复现的失败次数、成功重跑次数、已审查的样例数、已迁移的记录数、已处理的评论数，或已验证的案例数

4. 在设定之前修复薄弱的目标。
   - 当本地上下文使得重写是安全的时，将模糊的目标重写为可衡量的目标。
   - 当缺失的细节会改变预期的结果或验证方式时，提出一个简洁的澄清问题。
   - 拒绝纯粹的活动性目标，例如"取得进展"、"继续调查"、"改善一些东西"或"处理X"，除非它们被打磨成一个可验证的结果。

5. 在创建目标之前检查当前活跃的目标状态。
   - 调用 `get_goal`。
   - 如果没有活跃的目标，并且该目标达到了质量标准，调用 `create_goal`。
   - 如果存在一个仍与用户意图匹配的活跃目标，继续使用它，而不要创建一个重复的目标。
   - 如果存在一个与新请求相冲突的活跃目标，询问应该完成当前目标、如果已完成则将其标记为完成，还是开始一个单独的、由目标驱动的新线程。

6. 只有在目标通过质量标准之后才创建它。
   - 使用一个单一、简洁的目标字符串。
   - 将验证证据包含在目标本身之中。
   - 当范围边界会限制工作时，包含它们。
   - 只有在用户明确要求时才包含令牌预算。
   - 除非用户明确要求进行目标驱动的工作，否则不要为一个普通的多步骤任务调用 `create_goal`。

## 目标质量标准

在调用 `create_goal` 之前，该目标应该能回答：

- 完成后将成立的具体事情是什么？
- 什么证据能证明这一点？
- 什么量化或二元的门限定义了成功？
- 哪些范围边界很重要？
- 什么情况应该导致代理停下来询问？

好的示例：

> 通过做出最小、安全的服务端更改，将文档中记录的慢路径的结账API p95延迟降低到250毫秒以下，然后用 `npm run test:checkout` 和现有的本地延迟基准测试进行验证，该基准测试需在连续3次运行中显示p95低于250毫秒。

好的示例：

> 解决PR 123上要求代码更改的未处理评审意见，仅更新受影响的auth文件和测试，并用针对性的auth测试命令以及 `gh pr view 123`（显示没有未解决的变更请求线程）进行验证。

薄弱的示例：

> 让结账更快。

薄弱的示例：

> 继续调查PR的评论。

## 量化启发法

- 对于bug，将成功定义为先复现、后修复，并尽可能有一个先失败后通过的验证器。
- 对于测试，指明确切的命令和所需的通过条件。
- 对于性能，指明指标、目标门限、测量方法以及运行次数。
- 对于质量工作，定义一个可观察的验收标准，例如已审查的样例、通过的lint/类型检查/测试，或经用户批准的产物。
- 对于研究，定义该研究必须支持的决策、范围内的来源或系统，以及证据标准。
- 对于运维，定义健康状态、监测窗口、失败门限，以及回滚或升级触发条件。

## 澄清性问题

只有当一个合理的重写会有追求错误结果的风险时才提问。保持问题简短，并围绕缺失的验证器或范围边界来提问。

有用的问题形式：

- "这里应该用什么指标来定义成功：延迟、成本、准确率，还是用户可见的行为？"
- "我应该针对哪个环境进行验证：本地、预发布，还是生产环境？"
- "在我将此目标标记为完成之前，你想要的最低证据是什么？"

如果用户无法提供一个指标，提出可用的最诚实的二元验证器，并请求确认。
