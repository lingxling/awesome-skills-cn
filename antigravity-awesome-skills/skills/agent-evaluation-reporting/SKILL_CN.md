# 智能体评估报告

## 概述

将原始的智能体评估运行结果转化为可用于决策的报告，既不掩盖失败，也不夸大能力。明确保留结果总体、分母、延迟统计总体和实验条件，使读者能够复现每一个核心数字。

## 何时使用此技能

- 用于汇报 AI 智能体的基准测试、回归测试、试点或生产环境评估运行结果。
- 用于同一结果集中同时包含自主完成与人工辅助完成的情况。
- 用于失败、超时、基础设施导致的无效运行、重试或部分结果会影响分母的情况。
- 用于比较两个智能体、提示词、测试框架（harness）或版本，并判断该比较是否有效。

## 工作原理

### 步骤 1：冻结比较契约

记录任务集与抽样方式、模型与提供商、提示词或策略版本、工具与测试框架版本、评估者评分标准、超时与重试策略、token 或成本预算、运行环境以及人工介入策略。为该配置分配一个稳定的标签或摘要值。

如果两次运行之间存在实质性的条件差异，则将该比较标记为非等价比较。仅报告方向性观察；不要声称是被改动的智能体导致了差异。

### 步骤 2：构建互斥的结果台账

将每一次计划内的尝试恰好归入一个类别：

| 结果 | 含义 |
|---|---|
| `autonomous_success` | 智能体在没有人工介入的情况下满足了评估者的要求。 |
| `assisted_success` | 任务仅在人工介入之后才成功。 |
| `failure` | 运行达到了终态且可评估的失败。 |
| `timeout` | 运行耗尽了其声明的时间或步数预算。 |
| `invalid` | 由于测试框架、环境或输入出错，智能体从未获得有效的评估。 |

在可获得时，保留尝试 ID、任务 ID 或随机种子、重试序号、父尝试 ID、配置标签、结果、介入次数、时长、成本、评估者证据以及无效原因。绝不要悄悄丢弃无效运行或被重试的运行。

同时构建按唯一任务汇总的视图。对每个任务，保留其首次尝试的结果，并在预先声明的重试策略执行完毕后推导出一个最终结果。一次执行尝试在尝试级指标中只能计入一次，而一个任务在任务级完成指标中也只能计入一次。如果缺少重试谱系或重试策略，则不要报告任务的最终完成率。

### 步骤 3：为每个指标锁定分母

令 `N_all` 为所有执行尝试（包括重试），`N_eval = N_all - N_invalid` 为可评估的尝试。令 `T_all` 为计划内的唯一任务数，`T_eval` 为在固定重试策略下具有有效任务级结果的任务数。每个比率旁都要同时报告计数。

```text
autonomous attempt success = N_autonomous / N_eval
assisted attempt success   = N_assisted / N_eval
attempt non-completion     = (N_failure + N_timeout) / N_eval
invalid-attempt rate       = N_invalid / N_all
first-attempt completion   = T_first_attempt_completed / T_all
eventual task completion   = T_eventual_completed / T_eval
operational task delivery  = T_eventual_completed / T_all
```

明确标注尝试级指标与唯一任务级指标；绝不要把尝试级比率称为工作流完成率。报告重试率和每个任务的尝试次数，使依赖策略而获得的提升保持可见。检查可评估尝试的结果之和等于 `N_eval`，所有尝试的结果之和等于 `N_all`，且任务汇总之和等于 `T_all`。

如果 `N_eval == 0`，则将每个尝试级能力比率报告为 `unavailable`，而不是除以零，并将依赖这些比率的任何门禁标记为 `inconclusive`。对任何分母为零的指标都适用同样的规则，包括 `T_all == 0` 或 `T_eval == 0` 时的任务级比率。

### 步骤 4：如实保持延迟与成本的统计总体

分别报告自主完成延迟、辅助完成的端到端延迟以及失败的到达终态时间。仅针对成功运行的 P50 并不是整体 P50，并且子群的中位数不能通过平均或加权来重建合并后的中位数。

仅基于逐次运行的观测值计算全部运行的百分位数，并说明如何处理超时。如果时长是右删失的，则报告删失策略，或使用合适的生存分析估计。对 token 和成本指标采用同样的统计总体标注。

### 步骤 5：量化不确定性与可比性

对于具有随机性的评估，在核心比率旁展示样本量以及区间或多次运行的分布。对于比较，报告绝对差值，并验证双方共享步骤 1 中冻结的契约。如果数据缺失、条件不同或区间过宽，则使用 `inconclusive`，而不是强行选出优胜者。

### 步骤 6：将证据映射到预先声明的决策门禁

在查看结果之前就定义就绪门禁，例如最低自主成功率、最高超时率、零严重安全违规，以及延迟或成本上限。为每个门禁返回 `pass`、`fail` 或 `inconclusive`。

不要仅凭成功率推断生产就绪。如果未提供阈值或风险要求，则说明尚未判定就绪情况，并列出缺失的门禁。

## 示例

对于 120 个唯一任务、每个任务一次尝试的情形，其中包括 12 次基础设施导致的无效运行、48 次自主成功、24 次辅助成功、20 次失败和 16 次超时：

```text
Evaluable attempts:       108 / 120
Autonomous success:        48 / 108 = 44.4%
Assisted success:          24 / 108 = 22.2%
Attempt non-completion:     36 / 108 = 33.3%
First-attempt completion:   72 / 120 = 60.0%
Eventual task completion:   72 / 108 = 66.7% (no retries)
Operational task delivery: 72 / 120 = 60.0%
Infrastructure-invalid:    12 / 120 = 10.0%
Overall latency P50:       unavailable from subgroup aggregates
Readiness:                 inconclusive until gates are declared
```

## 最佳实践

- 将计数、公式、分母标签和排除项一并报告。
- 将自主能力与人工辅助的工作流完成情况区分开。
- 即使发布的是有效运行的得分，也要保留超时率和无效运行率。
- 将汇总指标与失败类别及代表性证据配合呈现。
- 在做出因果性的改进结论之前，于同一个冻结契约下重新运行两个候选方案。

## 局限性

- 此技能负责组织和解读所提供的评估证据；它不会验证评估者本身，也不会重建缺失的运行记录。
- 规模较小或有偏的任务集可能产生看似精确但不具代表性的指标。
- 统计显著性并不能证明生产环境的安全性、用户价值或可接受的成本。
- 当缺少验收阈值、严重性策略或所需证据时，就绪情况仍然是 inconclusive。

## 安全与保障说明

- 在报告中对凭据、私有提示词、个人数据和敏感的工具输出进行脱敏，同时保留稳定的证据引用。
- 将严重安全违规视为独立的发布门禁，而不是将其平均计入整体质量得分。

## 常见陷阱

- **问题：** 辅助完成被当作自主成功呈现。
  **解决方案：** 分别发布自主完成率、辅助完成率和工作流完成率。
- **问题：** 超时或无效运行从分母中消失。
  **解决方案：** 在计算指标之前，将完整的结果台账与 `N_all` 进行核对。
- **问题：** 仅针对成功运行的 P50 更快，却被呈现为系统更快。
  **解决方案：** 标注统计总体，并仅基于逐次运行的数据报告全部运行的到达终态时间。
- **问题：** 在看到结果之后才临时拟定发布结论。
  **解决方案：** 应用预先声明的门禁，否则返回 `inconclusive`。
