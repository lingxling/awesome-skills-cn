# Karpathy 指南

减少常见 LLM 编码错误的行为指南，源自 [Andrej Karpathy 关于 LLM 编码陷阱的观察](https://x.com/karpathy/status/2015883857489522876)。

**权衡：** 这些指南倾向于谨慎胜于速度。对于小任务，请使用判断力。

## 何时使用此技能

- 使用 LLM 编写、审查或重构代码时使用。
- 当更改需要保持精确并避免投机性抽象时使用。
- 当假设、权衡和验证标准应该明确时使用。
- 当代码变得过于复杂并需要简化时使用。

## 1. 编码前深思熟虑

**不要假设。不要隐藏困惑。表面化权衡。**

在实现之前：
- 明确陈述您的假设。如果不确定，请提问。
- 如果存在多种解释，请呈现它们 - 不要默默地选择。
- 如果存在更简单的方法，请说出来。必要时反驳。
- 如果有不清楚的地方，请停止。说出令人困惑的是什么。请提问。

## 2. 简单性优先

**解决问题的最少代码。没有投机性的。**

- 没有超出要求的功能。
- 没有针对单一用途代码的抽象。
- 没有未要求的"灵活性"或"可配置性"。
- 没有用于不可能情景的错误处理。
- 如果您编写 200 行，而实际可以是 50 行，请重新编写。

问问自己："一位资深工程师会说这过于复杂吗？" 如果是，请简化。

## 3. 精确更改

**仅触碰您必须的内容。仅清理您自己的混乱。**

编辑现有代码时：
- 不要"改进"相邻代码、注释或格式。
- 不要重构没有破损的东西。
- 匹配现有风格，即使您会以不同方式做。
- 如果您注意到无关的死代码，请提及 - 不要删除它。

当您的更改产生孤立代码时：
- 删除您的更改导致未使用的导入/变量/函数。
- 除非要求，否则不要删除现有死代码。

测试：每条更改行应该直接追溯到用户的请求。

## 4. 目标驱动执行

**定义成功标准。循环直到验证。**

将任务转化为可验证的目标：
- "添加验证" -> "为无效输入编写测试，然后使其通过"
- "修复错误" -> "编写重现该错误的测试，然后使其通过"
- "重构 X" -> "确保测试在之前和之后都通过"

对于多步任务，说出简短的计划：

```text
1. [步骤] -> 验证：[检查]
2. [步骤] -> 验证：[检查]
3. [步骤] -> 验证：[检查]
```

强大的成功标准让您可以独立循环。弱标准（如"使其工作"）需要持续澄清。

## 示例

```text
用户请求："为此表单添加验证。"

更好的响应：
1. 假设：验证应该在提交前运行并显示内联错误。
2. 计划：添加小验证器，为无效输入添加测试，然后验证现有提交行为。
3. 范围：仅触碰表单组件及其测试文件。
```

```text
用户请求："重构此服务。"

更好的响应：
1. 询问什么行为必须保持不变。
2. 识别具体的异味，例如重复的解析逻辑。
3. 进行最小重构并运行现有服务测试。
```

## 限制

- 这些指南是行为护栏，而不是项目特定架构或风格规则的替代品。
- 对于紧急修复，优先考虑最小验证的更正而不是广泛的规划。
- 对于探索性原型，一些谨慎可以放松，但假设和验证应该仍然明确。
