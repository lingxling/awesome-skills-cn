# Antigravity 维护者批量发布

## 何时使用

将此技能用于仓库范围的 AAS 维护、维护者侧的 PR 修复或合并批次、规范同步、AAS Core 或 Workbench 变更、受保护发布,以及托管目录或旧版重定向基础设施。不要将其用于不需要维护者权限或规范收敛的普通贡献工作。

## 受保护 main 合约

将包含此技能的仓库根目录视为仅接受 pull request:

- 在变更之前阅读 `AGENTS.md`、`.github/MAINTENANCE.md` 和当前的维护者文档。
- 即使用户说"推送到 main",也绝不要直接向 `main` 提交或推送。那句话指的是最终目标状态。
- 保留与任务无关的脏工作区改动。为维护者变更使用干净的临时克隆或主题分支。
- 对已接受的来源 PR 使用 `npm run merge:batch`。不要用原始合并 API、通用 GitHub 技能或通用推送辅助工具替代。
- 让 `automation/canonical-repo-state` 负责生成的工件和来源批次之后的贡献者署名收敛。该流水线运行 `sync:repo-state`,现在还会通过 `sync:top-contributors` 重新计算 README 中的 `## Top Contributors` 排行榜:绝不要手工编辑这些表格,将过时的排名视为生成器或排除列表的缺陷。
- 对发布使用 `release:prepare` 和 `release:publish`。它们绝不会授权直接推送 `main`。

## 来源检查

在改动任何内容之前:

1. 拉取 `origin/main`;证明干净的维护者工作副本处于 `main` 分支且等同于 `origin/main`。
2. 检查范围内的活跃 PR、issue、讨论,Actions 失败、Dependabot、CodeQL、secret scanning,以及相关的 `npm audit`。
3. 确认 `package.json` 中的当前脚本以及**当前 CI 工作流**中列出的工作流文件;不要依赖记忆中的 CI 或发布行为。
4. 单独记录用户工作区状态,并将这些文件排除在维护者提交之外。

## 当前 CI 工作流

阅读 `.github/workflows/ci.yml`、`.github/workflows/skill-review.yml`、`.github/workflows/skillspector-advisory.yml` 及其在确切任务基准上的受保护基准脚本。任务依赖关系定义执行顺序;文件顺序和绿色的工作流徽章并不定义合并权限。

### 必需的 PR 检查和独立审查

| 环节 | 实际顺序和证据 |
| --- | --- |
| 准入 | `pr-policy` 最先运行。普通来源 PR 使用确切的受保护基准分类器及其依赖项来进行 fork 安全和仅限来源策略的检查。 |
| 来源验证 | 在 `pr-policy` 之后,`source-validation` 检查来源、刷新一次临时生成状态、验证适用的引用、运行完整未分片的测试套件和文档安全检查,并上传确切头部的预览清单。 |
| 已变更技能证据 | 同样在 `pr-policy` 之后,`pr-evidence` 与 `source-validation` 并行运行。它发布已变更技能的证据和影子决策清单,然后强制执行确定性回归检查。其咨询性质的语义审查状态并不能替代单独的 skill-review 结果。 |
| 工件预览 | `artifact-preview` 等待 `pr-policy` 和 `source-validation`,验证来源预览清单及其仓库/头部/工作流/运行尝试的绑定关系,且不会为普通来源 PR 重新生成工件。它不等待 `pr-evidence`。 |
| 语义审查 | 独立的 `skill-review.yml` 工作流对完整的已变更技能目录树进行指纹识别。"review"(通过)意味着 Tessl 结果通过,或者有效的相同内容复用;"manual-review-required"(需人工审查)需要维护者的语义审查和确切的完整头部认证。它独立于必需的 CI DAG。 |
| 静态咨询扫描 | 独立的、仅在 PR 上运行的 `skillspector-advisory.yml` 工作流先运行 `evidence-ready`,再运行 `skillspector-advisory`。它等待同一 PR 和确切头部 SHA 的最新 GitHub Actions `pr-evidence` 检查,独立于 `source-validation`、`artifact-preview` 和语义审查。 |

四项常规受保护检查依然是 `pr-policy`、`pr-evidence`、`source-validation` 和 `artifact-preview`。要真实地审查技能内容变更,并在需要确切头部认证时使用 `merge:batch`。SkillSpector、Jev、影子决策和计时遥测数据都不能满足这些检查,也不能授权合并。在语义审查期间检查可用的咨询性发现,但不要将咨询工作流添加到分支保护、fork 运行批准前提或 `merge:batch` 中,除非有单独授权的合约变更。

对于受保护的规范同步 PR,`pr-policy` 会从受信任的 `main` 复现确切的受管理树;`source-validation` 和 `pr-evidence` 记录轻量级的成功边界检查,而 `artifact-preview` 会重新生成以确认没有漂移。不要将这些边界检查任务描述为新的来源测试或语义扫描。在合并后的 `main` 上,`main-validation-and-sync` 执行仓库状态同步、引用验证、依赖审计、完整测试、网页覆盖率和文档安全检查。只有当存在受管理的漂移时,它才会创建或更新受保护的规范 PR。等待该 PR 的受保护合并完成,然后验证最终的 `main` CI、CodeQL、干净的工作树和幂等的生成状态。此路径不授权发布或 Pages 部署。

### SkillSpector 咨询 CI

将当前的 `.github/workflows/skillspector-advisory.yml` 和 `tools/scripts/skillspector_advisory.py` 作为实现合约:

1. `evidence-ready` 轮询确切头部的检查结果,查找由 GitHub Actions app ID `15368` 关联到同一 PR 编号的 `pr-evidence` 结果。它最多进行 60 次轮询,间隔 10 秒,任务超时时间为 12 分钟。检查失败或超时意味着没有运行扫描。该工作流只有 `pull_request` 触发器,针对 `main`;没有手动、push 或特权触发器。
2. 咨询任务检出 PR 的受保护基准,禁用持久化的 Git 凭据,以数据形式获取不可变的 PR 头部,并规划已变更的规范 `skills/<skill-id>/**` 目录。复制只改变其目标;重命名会检查两个路径根。仅限插件的镜像变更在该扫描器的规范范围之外。没有 `SKILL.md` 的已删除根目录会记录为 `deleted-or-no-skill`。
3. 当规划出的技能列表为空时,会跳过安装和扫描。先检查 `manifest.json`:带有 `errors` 的空列表可能意味着超出限制,而不是扫描为空或成功。在受保护基准上缺少包装器会产生记录在案的 bootstrap 跳过。绿色的 bootstrap 或仅规划的运行并不能证明 SkillSpector 真的执行了。
4. 对于已规划的技能,使用 Python 3.12、`uv==0.8.22` 和 `uv sync --frozen --no-dev`,在不可变提交 `c7958a3268d9498644b22edb75d0f051bbc8cbfc` 上安装 NVIDIA SkillSpector v2.12.0。将完整的已变更规范树从 Git 复制到私有的惰性快照中。可执行的二进制对象以 `0600` 权限复制,并列在 `executable_git_blobs` 下;它们永远不会被调用。链接、gitlink、不支持的模式和无效路径会被拒绝。该扫描器快照与确定性证据评估器更严格的可执行文件拒绝机制是分开的。
5. 以运行器用户身份在 Linux 网络命名空间中运行 `--no-llm`,使用经过清理的扫描器环境并禁用追踪。单独的静态模式并不能保证离线行为;命名空间还能阻止 OSV 等网络请求。不应用任何贡献的基线或自动抑制。
6. 遵守实现上的限制:每次最多 50 个已变更技能根目录、每个技能最多 1,000 个文件和 16 MiB、每次扫描器调用最多 60 秒、每两个技能之间检查一次的 600 秒总预算、每份 JSON 报告最多 8 MiB,以及 15 分钟的咨询任务超时。缺失、格式错误、过大、超时或不受支持的输入都算作不完整;绝不要将没有输出视为干净的扫描结果。
7. 读取保留 14 天的 `skillspector-advisory-<PR_NUMBER>` 工件及扫描步骤的结果。清单中的 `head_sha` 是实际被扫描的头部;`base_sha` 是解析出的 Git 合并基准。使用报告前先比较这些绑定关系。该任务设置了 `continue-on-error: true`,因此其整体绿色结果本身并不代表扫描器通过或安全认证。

根据实际报告而非工作流徽章来解读清单状态:

| 状态 | 含义和维护者操作 |
| --- | --- |
| `dry-run` | 规划复制了目录树但未调用扫描器。查找后续的扫描报告。 |
| `deleted-or-no-skill` | 该头部在该根目录没有规范的 `SKILL.md`;未对其运行扫描。 |
| `reported` | 退出码为零,执行成功,分析标记为完整。检查 `finding_count` 和完整的 JSON;这不是合并批准或通用安全保证。 |
| `partial` | 退出码为零、执行成功,但分析不完整。检查报告的限制和覆盖范围。 |
| `scanner-nonzero` | 退出码非零或执行不成功。检查 `exit_code`、`finding_count`、`execution_successful`、`analysis_complete` 和完整的 JSON:非零退出码可能表示发现了问题而非操作失败。 |
| `incomplete` | 快照被拒绝、超时、输出格式错误/缺失,或其他被捕获的操作错误。阅读记录的错误;不要推断为干净的结果。 |

在试点阶段逐个审查发现项。缺少 `allowed-tools`、发送到 API 的环境凭据、低风险分数以及带有攻击性教育目的的示例都需要结合上下文和声明的用途来判断。不要批量接受一个基线或静默抑制报告。任何后续的抑制策略或阻断规则都需要单独审查的工作流合约变更。正式的技能内容审查仍然是 Tessl 或确切头部的维护者认证。

### SkillSpector 分类校准

在将原始发现计数视为缺陷计数之前,应结合仓库自身语料的形态进行校准。一次完整的静态维护扫描会打印出数千条发现,其中大多数只是扫描器在描述文档,而不是技能在行动:

- 行文占主导。大约十分之九的发现位于 `SKILL.md`、README 和 `references/**` 的行文中。一份记录了 `Ignore all previous instructions` 或 `.env` 处理方式的安全参考文档是在描述一种攻击,而不是在实施攻击。先分类可执行的部分:出现在实际交付的 `.py`/`.js`/`.sh`/`.ts` 文件中而非 `.md` 文件中的发现,才是值得代码审查的。
- 针对 `.env`、`access_token` 或 `keychain` token 的 `Credential Access` 发现通常只是读取配置,甚至可能是像 `--exclude='.env'` 这样的防护措施。在将其视为提权之前,先通过阅读该行代码确认意图。
- 具有攻击性设计用途的技能(渗透测试、漏洞利用、提权、逆向工程)会命中攻击性模式,因为那正是它们声明的用途和风险标签。不要将它们计为回归,也不要用它们的分数来做门控。
- `partial`(部分)/ 不完整的分析是静态模式的默认结果,不是仓库缺陷。它意味着至少一个分析器被降级运行,或某个有边界限制的解析器达到了其跨度上限。
- 捆绑的测试固件树(生成的应用、基准测试、`examples/**`、录制的会话)会用技能本身并未作为指导内容交付的代码拉高该技能的分数。应清理打包方式,而不是去修补固件中的漏洞。

当确认存在真实的可执行缺陷时,通过常规的验证和 PR 流程在来源技能中修复,并将扫描器视为咨询性输入。经过校准后,头条发现数量大幅减少是预期结果,不是无法解释的差距。

正式的技能内容审查仍然是 Tessl 或确切头部的维护者认证。

## 维护者批量操作

1. 在编辑之前对每个开放的 PR 进行分类。
   - 区分有效的来源变更、可修复的 PR、冲突、仅生成内容的噪音、推广链接,以及不受支持的所属权/许可证变更。
   - 审查语义、安全性、来源、风险标签、限制、来源署名和已变更技能的证据。
   - 当维护者编辑可用时,优先在贡献者分支上进行小范围的维护者修复。
   - 编辑前的可选加速步骤:运行 `npm run maintainer:sweep` 以获取仓库健康状况、开放 PR 检查汇总、CI `pr-evidence-*` 工件的咨询性下载(当 `pr-evidence` 成功时)、可选的 Jev 分类(`.env.local` 中的 `TYPESAFE_API_KEY`)、对 CI 就绪的 PR 执行 `merge:batch --dry-run`,以及一份**下一步操作**提示列表。当工件头部匹配时,优先使用 CI 证据而不是本地重新运行 `npm run pr:evidence`。对于单个头部,使用 `npm run maintainer:jev-hints -- --base origin/main --head <head-sha>`。Sweep/Jev/CI 汇总只是咨询性的;`merge:batch` 会从受信任的 `main` 重新计算,Tessl 加上 `--reviewed-head` 认证仍是权威依据。参见 `docs/maintainers/maintainer-sweep.md` 和 `docs/maintainers/jev-hints.md`。

2. 真实地验证已变更的技能。
   - 运行 `npm run validate`、`npm run validate:references`、`npm run security:docs`、已变更技能证据检查,以及相关测试。
   - 将整个被跟踪的 `skills/<skill-id>/**` 子树视为技能内容。直接检查语义、安全性、来源、声明的风险、限制以及每个捆绑文件,包括嵌套的示例、脚本、锁文件、引用和资源。绝不要将证据或审查范围缩减到 `SKILL.md` 或固定的支持目录白名单。
   - 要求已变更技能证据覆盖每个已变更规范技能子树中的每条 Git 记录。要求在 `skills/**` 或 `plugins/**/skills/**` 下的变更运行 `skill-review` 工作流;其可复用的结果必须以确切当前头部 SHA 上完整最近技能目录指纹作为键。
   - 保持规范技能所属权查找与已变更路径的深度而非注册表总规模成比例,并保留五分钟的受信任评估器预算,使仓库级证据能够在不削弱失败关闭检查的前提下完成。将遗留的可执行模式规范 `SKILL.md` 仅作为私有、非可执行的快照数据解析;保持将其报告为不安全,绝不要物化符号链接、gitlink 或其他可执行文件。
   - "review"(通过)意味着 Tessl 语义审查确实运行过,或者复用了有效的相同内容结果。
   - "manual-review-required"(需人工审查)意味着 Tessl 凭据或额度不可用,或 Tessl 没有产生通过的结果。执行维护者语义审查,并使用 `--reviewed-head <full-40-character-sha>` 进行认证。
   - 任何非通过的 Tessl 结果都会产生 `manual-review-required`;完成语义审查,并将判断绑定到确切头部,而不是将启发式分数当作合并权限。
   - 绝不要把 `manual-review-required` 报告为"Tessl 已通过"。
   - 范围内容审查指纹记录的是确切字节和已观察的检查,而不是通用可靠性。保持明确的兼容性别名及其完整的本地支持包同步;别名完整性回归检查只验证相等性,不影响选择资格。报告剩余的语料库债务,而不是颁发一个无条件的验证徽章。
   - 经过验证的上游仓库重命名只能通过受信任的受保护基准异常名册中的确切条目来绕过来源身份阻断。记录技能 ID、新旧 `source_repo`、稳定的上游仓库 ID、验证日期和规范的 GitHub URL;其他所有来源变更仍将被阻断。

3. 在独立的情况下并行运行检查。
   - 按照下方**当前 CI 工作流**中的环节执行。阅读可用的 SkillSpector 报告及其清单状态和确切头部绑定;绝不要把仅规划、部分或绿色的咨询性运行与完整的语义审查混淆。
   - 使用受已变更文件要求的仓库验证、测试、文档安全、来源署名、引用、警告预算和针对性应用检查。
   - 在来源中修复确定性的策略失败;不要像对待不稳定的 CI 那样等待它们。
   - 对于仅限来源变更的路径,Git 的复制只会改变其目标路径;重命名会改变两个路径。在 fork 分类器中也要将 Git 复制来源视为只读:Git 根据相似度将复制与基准树中已存在的任意路径配对,因此该来源的路径类别并不受作者控制,同一个新规范技能不应因 Git 选择了哪个既有文件而通过或失败。保留其原始记录、模式、对象、大小和总预算检查,并将编辑、重命名或删除该来源视为确定性的失败。
   - 将来自确切受保护基准实现的 `pr-policy` fork 分类视为无特权的快速失败门,而不是批准权限。从同一受保护基准工作区安装并解析该分类器使用的每个依赖项;绝不要将其暴露给受 pull request 控制的 `node_modules`。在批准任何 fork 运行或合并之前,`merge:batch` 仍必须重新计算当前受信任的决策。准入白名单还覆盖 `apps/web-app/src/**` 下的浏览器来源(`.css`、`.ts`、`.tsx`);这些 fork 运行可以被批准,但每一个 web-app 来源变更在合并前仍需要确切头部的维护者认证。还要将在 fork pull request 上运行的每个只读、仅限 PR 的工作流保留在批准白名单中:即使该工作流本身只声明只读权限、不使用秘密,并且将其操作固定到完整 SHA,遗漏它仍会导致这些 PR 停留在 `action_required` 状态而没有任何门控可以合并。
   - 将 `impact_profile` 视为仅供影子使用的遥测数据。它绝不能跳过、降级或满足任何必需检查。
   - 对于普通来源 PR,要求 `source-validation` 只生成一次预览状态,并要求 `artifact-preview` 验证绑定到确切头部和运行身份的清单。对于规范同步 PR,依赖 `pr-policy` 的确切树复现,保持 `source-validation` 轻量化,要求 `artifact-preview` 确认无漂移,并在合并后的 `main` 提交上保留最终的 CI 和 CodeQL。
   - 保持计时仅作观察用途,测试分片为可选启用项。必需的 CI 必须继续运行完整未分片的 `npm run test`;确定性的本地分片只能通过 `npm run test:local -- --shard-index N --shard-count M` 使用。

4. 以对冲突敏感的顺序合并已接受的来源 PR。
   - 在有用时先进行一次干运行分类。
   - 对于已变更的技能内容,审查确切头部并运行:

     ```bash
     npm run merge:batch -- --prs <PR_LIST> --reviewed-head <FULL_HEAD_SHA>
     ```

   - `merge:batch` 不会重写 PR 正文,也不会关闭或重新打开 PR。它评估当前不可变的 PR 元组,且只能批准绑定到该 PR 和确切头部 SHA 的工作流运行。
   - 同一仓库的位置本身不足以构成敏感变更的授权。受保护的同仓库例外仅限于由仓库所有者撰写的 PR,且需要确切的完整头部认证;协作者撰写的敏感 PR 在外部安全策略下将失败关闭。
   - 常规受保护检查是 `pr-policy`、`pr-evidence`、`source-validation` 和 `artifact-preview`。已退役的 `aas-v1-baseline` 工作流不是合并前提条件,在来源或规范同步批次中不得等待或批准它。
   - 如果 PR 头部或基准发生变化,丢弃陈旧的证据,刷新到当前的 `origin/main`,并重新运行该批次。该命令不会自动重试基准漂移。

5. 在来源批次之后一次性收敛规范状态。
   - 等待受保护的 `automation/canonical-repo-state` PR。
   - 验证其仅受管理的差异、必需检查、合并结果以及最终的 `origin/main`。
   - 如果仍有未受管理的修复,使用主题 PR;绝不要直接修补 `main`。


### 已审查的 fork 捆绑例外

`tools/config/reviewed-fork-skills.json` 是一个受保护基准名册,记录
已明确审查过的 fork 贡献。每条记录绑定基础仓库、
fork 仓库、PR 编号、原始完整审查头部和完整的 Git
技能树对象。基线规则只允许 Markdown/资源/引用
支持文件、该技能 `scripts/` 子树下的 Python 文件及其根
`LICENSE`,以及在需要时的只读 Git 复制来源。一条记录可以选择加入
其自身技能根目录内最多 16 个额外的确切路径;验证器只能
表示根清单文件(`.gitignore`、`README.md`、`LICENSE`)和
`scripts/*.py`,因此它永远不能成为通用的扩展白名单。它不
允许工作流、任意脚本类型、生成文件的变更、不安全的模式、
链接、无效路径/对象或超大内容。

CI 准入和 `merge:batch` 都从各自受信任的评估器
工作副本加载名册,而不是 PR 的仓库目录。技能子树中任何位置的任何变更
都会使该例外失效。仅涉及基础部分的合并可以复用相同的内容,
但维护者必须检查新的完整 PR 差异,并用 `--reviewed-head` 认证
其确切的当前头部。证据、仅限来源的检查、真实的技能
审查、不可变的 PR/工作流绑定和严格的分支保护都仍然
是强制性的。缺失或格式错误的名册数据将失败关闭。进一步的例外或
策略扩展需要维护者的明确授权和受保护审查。

## AAS Core 预览验收

对于 AAS CLI、MCP、stack、catalog-cache 或 Workbench 变更:

1. 使用 `package.json` 中声明的当前脚本;不要将已退役的评估器、基准测试、调优黄金集、事务故障、竞态或冻结矩阵门控作为常规前提条件复活。
2. 使用 `npm run test:aas-v1` 运行针对性的 Core 测试,使用 `npm run check:aas-v1-catalog` 运行目录完整性检查,并在 Workbench 的合约或文案发生变更时运行相关的 Workbench 测试/构建。
3. 保持 MCP 本地、离线、只读、有边界、不进行变更操作。编码代理检查项目、搜索并读取完整目录,并选择确切的技能 ID。MCP 进行搜索、读取、验证代理自有的组合,并进行比较,而不扫描仓库或向其写入内容。Core 不得对技能进行排名、推荐、排除或禁用;元数据仅供参考。
   - 对于捆绑包检查变更,验证绑定到目录的文件清单和逐次读取的摘要值、路径遍历/链接拒绝、二进制和大小限制、旧版目录行为,以及来自实际打包运行时的支持文件读取。绝不要执行被检查的脚本或获取缺失的有效载荷。保留所有规范 ID,包括那些文件无法通过文本接口读取的技能。
   - 调用方明确提供的搜索过滤条件可以缩小检索范围;它们永远不能定义技能的资格。对于搜索变更,验证向后兼容的宽泛匹配、全词匹配、有边界的过滤器、类别别名、稳定的分页、在没有过滤器时的完整目录可达性,以及通过证据导出和检查保留所提供的选项。
4. 保持 `aas-stack.json` 不含 Core 选择策略。它只固定目录身份、目标、目标描述和代理选择的确切 ID。`compose_stack` 验证并记录该选择;缺失或警示性的元数据绝不能使某个规范技能变得不可选或不可用。
5. 保持受支持的公共路径仅限于清单验证和不可变的计划预览。规划只能写入所请求的计划工件;它不能物化技能有效载荷或在目标中物化 AAS 受管理状态。
   - 验证清单到安装器命令的准备过程保留了代理选择的确切 ID 和目录版本,拒绝空的或未知的选择,对 shell 参数加引号,并只生成一次干运行。运行时自动解析必须保持离线且有边界,完整验证缓存的字节内容,并拒绝多重已验证身份;绝不要从运行时或元数据检查中推断技能适用性。在临时目标中执行实际的打包安装,比较所有选定文件的字节内容,重复执行,保留未受管理的文件,并拒绝已移动发布和符号链接目标的情况。将固件发布解析与真实的已发布版本/客户端检查区分开;汇总结果必须拒绝缺失的安装证据。要求同时具备 Linux 和 Windows 的打包接收证明。在一次性的 Windows 运行器上同时用 PowerShell 7 和 Windows PowerShell 5.1 执行生成的 PowerShell 命令,记录并检查两种实际的 shell 版本,包括含空格和撇号的路径、完整的有效载荷比较、重复/修剪行为以及对联接点(junction)的拒绝。本地 Git/发布固件不能证明注册表的可用性或真实客户端会话。
   - 只对经过验证的单目标清单推断目标;否则要求明确选择。验证缓存的运行时的目录与清单匹配,并保持运行时完整性、缓存位置和目标的明确性。记录单独的直接安装器交接方式,而不暗示其适用于 Core 计划。
   - Workbench 的证据导入必须保持有边界且仅在内存中。验证工件摘要值、项目引用、清单/目录/配置文件/选择的绑定关系、冲突显示以及对陈旧结果的替换。将浏览器检查与完整的 Core 检查和语义判断区分开记录。记录的示例需要真实的输入和已观察的检查;可选的反馈只能在明确操作之后导出用户输入的字段,不包含遥测数据或导入的项目数据。
   - 通过真实的 stdio 而不仅仅是进程内处理器来验证大型清单和证据的来回传输。工件参数可以使用现有的 256 KiB 帧上限;普通请求和不相关的元数据仍受限于 4 KiB。被拒绝的、安全解析的请求必须保留一个有边界的请求 ID;绝不要反射格式错误或无边界的 ID。保持过载错误与有边界、严格解析的请求 ID 相关联;有效的通知不会收到响应,包括在队列已满或处理器失败的情况下。拒绝无效的信封而不反射无效的 ID,并通过真实 stdio 测试突发路径。
6. 将 apply 和 recovery 视为受支持预览声明之外的实验性可选项。除非用户明确将其纳入范围,否则不要添加 apply/recovery、基准测试、fuzz、崩溃/竞态或合成验证器工作。
7. 当任务要求端到端客户端证明时,使用能够发现并调用本地 AAS MCP 工具的真实受支持客户端;直接的 stdio 探测和自动化测试不能替代这种证据。
8. 在没有单独所需的发布批准的情况下,不要打标签、发布 npm 包、部署 Pages,或写入真实的用户 MCP 配置。

## 受保护发布

仅在被要求时才发布。

每个稳定版或预发布版本都需要完整的发布对齐。创建标签、GitHub Release 或 npm 包只是一个中间里程碑,绝不是完成条件。

1. 将目标变更日志条目包含在维护者批次 PR 中,使其已经处于受保护的 `main` 上;避免单独的、仅含发布说明的 PR。
2. 从干净的、最新的 `main` 开始,运行 `npm run release:preflight` 和所需的安全检查。
3. 运行发布状态生成器及其明确的插件门控检查。在发布前要求一次额外的无漂移检查:`npm run sync:release-state`、`npm run plugin-compat:check` 和 `npm run bundles:check` 都必须留下干净的工作树。检查 `package.json`、`package-lock.json`、生成的注册表和离线目录、被跟踪的网页资源、`.agents/plugins/marketplace.json`、`.claude-plugin/plugin.json`、`.claude-plugin/marketplace.json`、每个已发布的 Codex/Claude 插件镜像,以及每个符合条件的 Agent Plugins 编辑捆绑清单。每个发布所拥有的清单版本都必须等于 `X.Y.Z`。
4. 运行 `npm run release:prepare -- X.Y.Z`。这会创建并推送 `release/vX.Y.Z`,并打开受保护的发布 PR。
5. 通过其所需检查合并该发布 PR,将本地 `main` 更新为等同于 `origin/main`,并等待发布路径中的每个来源、发布或规范同步 PR 都关闭。如果受保护的 `main` 发生了移动,重新运行发布状态和插件门控检查。
6. 运行 `npm run release:publish -- X.Y.Z`。它必须从同一仓库中解析出恰好一个已合并的发布 PR,该 PR 由仓库所有者撰写,基准为 `main`,标题确切为 `chore: release vX.Y.Z`,头部分支为 `release/vX.Y.Z`。零个或多个候选项都会失败关闭;绝不要选择最新的近似匹配项。该命令随后会验证该确切的受保护合并,然后再创建或复用标签和 GitHub Release。
   npm 发布工作流必须先检出受保护的 `main`,验证剥离后的发布标签是当前 `origin/main` 的祖先,直接根据标记的 `package.json` 验证版本,然后才检出或执行受标签控制的代码。它没有手动触发的绕过方式。
7. 等待发布工作流完成,然后将每一项证明都绑定到确切已发布的提交:验证标签/引用、GitHub Release、npm 版本和预期的 dist-tag、所需的 CI、CodeQL,以及使用 `deployment_target=release` 从确切不可变的 `vX.Y.Z` 标签构建的发布标签 Pages 构建。绝不要从 `main` 或其他分支手动触发发布标签构建。单独的 `deployment_target=main` 触发可以在来源和规范同步工作完成后发布受保护的 main 提交;它必须在构建前和部署前分别验证当前 main 的身份。标记为 `[skip pages]` 的规范同步提交永远不会被规范同步触发。验证实时的 `llms.txt`、`skills.json`、目录和插件路由,以及旧版重定向桥接;不要接受针对不同 SHA 的成功运行。
8. 在 npm 确认 `X.Y.Z` 为已发布的 dist-tag 之后,从其真实配置中发现每一个已配置的本地 AAS MCP 主机,并在宣布发布完成之前将每个主机更新到完全相同的包版本。更新已存在的 AAS 主机条目是发布的一部分;创建之前不存在的主机配置仍需要明确授权。
   - 使用已发布包的 `aas mcp configure` 两阶段流程:先预览变更,再用完全相同的命令和其批准摘要重复一次。提供绝对的主机配置、缓存和备份路径;替换已存在的配置时要求备份。
   - 固定 `agentic-awesome-skills@X.Y.Z` 和 `--version X.Y.Z`;绝不要使用 `latest`、复用较旧的缓存运行时,或在没有明确授权的情况下创建之前不存在的主机配置。
   - 验证受管理的主机配置指向内容寻址的 `X.Y.Z` 运行时,运行时包元数据报告为 `X.Y.Z`,并且真实的 MCP `initialize` 加 `tools/list` 握手报告的目录包版本为 `X.Y.Z`。
   - 需要时重启主机或打开一个新的客户端会话,以便新的 MCP 进程确实被加载。如果配置访问、批准或运行时验证受阻,报告确切的阻断原因,并将维护任务标记为未完成,即使包本身已经公开。
9. 自动化完成后再次拉取 `origin/main`,快进维护者工作副本,并重复发布状态、插件、版本、公共表面和 MCP 一致性检查。最终的生成器运行必须是幂等的,工作树必须保持干净,且 `git rev-list --left-right --count main...origin/main` 的结果必须为 `0 0`。

绝不要对已发布的发布标签执行 rebase、强行伪造发布状态、复用失败的已发布版本,或仅凭 GitHub Release 就声称 npm 已发布。

## 停止条件

只有在以下条件满足时才算完成:

- 范围内的每个 PR、issue 和告警都已解决,或都有一个确切的阻断原因;
- 没有意外遗留的未关闭来源或规范同步 PR;
- 对于每个稳定版或预发布版本,干净的本地 `main`、`origin/main`、已发布的提交、规范生成状态、每个 Codex/Claude 插件镜像、符合条件的 Agent Plugins 捆绑清单、捆绑包、marketplace、兼容性报告、标签、GitHub Release、npm dist-tag、所需工作流和实时公共表面都完全一致;
- 来源仓库和旧版仓库没有意外的基础设施 PR,其受保护分支和 Actions 设置保持强制执行,且实时清单标明了来源仓库;
- 用户工作区除用户明确纳入范围的文件外保持不变;
- 当请求了发布时,发布证明是完整的,包括一次幂等的无漂移重新生成,以及已发布的 npm 包与每个已配置的本地 AAS MCP 主机之间的确切运行时一致性。任何不匹配都使发布视为未完成。

## 失败规则

- 受保护分支拒绝意味着切换到 PR 路径;绝不要重试直接推送 `main`。
- 缺少 PR 检查清单只是信息性的;绝不要仅为了刷新模板元数据而变更、关闭或重新打开 PR。
- 保留与任务无关的脏文件,绝不要将其纳入维护者的工作中。
- 不要用通用 Git 辅助工具绕过 `merge:batch`、规范同步或脚本化发布命令。
- 不要仅仅为了让某个批次通过而削弱测试或策略门控。只有在获得明确的维护者授权后才能退役某个门控,然后同时更新分支保护、工作流文件、合并自动化、文档和维护者技能,以确保不留下任何幻影要求。

## 示例

对于确切头部为 `0123456789abcdef0123456789abcdef01234567` 的已审查来源 PR,在合并前执行受保护路径:

```bash
npm run merge:batch -- --prs 914 --dry-run --reviewed-head 0123456789abcdef0123456789abcdef01234567
```

只有在每个必需检查都通过且被认证的头部保持不变之后,才运行不带 `--dry-run` 的相同命令。

## 限制

- 此技能编排的是仓库中已存在的脚本和受保护工作流;它不授予 GitHub、npm、Pages 或本地客户端的权限。
- 当发布、经过认证的配置或其他外部可见的操作未获授权时,在确切的批准或凭据边界处停止。
- 每次运行时都要重新阅读当前的仓库策略和 `package.json`,因为分支保护、检查和受支持的预览命令可能会发生变化。
