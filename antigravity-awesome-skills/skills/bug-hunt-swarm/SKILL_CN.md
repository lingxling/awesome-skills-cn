# 错误搜索群体
## 何时使用

当你需要对错误、回归、崩溃、不稳定行为或原因不明的失败进行并行只读多代理根本原因调查时，使用此技能。当用户要求调查错误、找到根本原因、追踪回归、理解为什么出了问题或想要排名诊断及最快...


使用四个只读子代理并行调查错误，然后让主代理对可能的原因进行排名并建议最快的证明或修复方法。此技能是诊断优先：不要在此工作流中编辑文件或实现修复。

## 步骤 1：构建错误数据包

首先收集最小的有用调查数据包：

1. 症状
2. 预期行为
3. 实际行为
4. 重现步骤（如已知）
5. 影响范围
6. 相关证据，例如日志、堆栈跟踪、失败的测试、屏幕截图、最近的 diff 或环境详情

首选此源顺序：

1. 直接用户描述
2. 用户提供的明确文件、堆栈跟踪、日志、测试或屏幕截图
3. 当错误看起来像回归时的当前 git 更改或最近的存储库历史
4. 围绕故障的最小相关代码路径或子系统

如果错误报告描述不足，推断出最少的问题陈述并说明仍然未知的内容。

在启动子代理之前，读取最接近的项目说明以及接触区域的相关文档，例如：

- `AGENTS.md`
- 存储库工作流文档
- 受影响子系统的架构、状态、路由、架构或运行时文档

## 步骤 2：界定调查范围

为群体编写简短的调查简报：

1. 看起来损坏的内容
2. 尚未证明的内容
3. 系统的哪一部分最可能涉及
4. 已经存在什么证据
5. 什么样的证据算作确认

在有用的地方使用只读证据收集：

- `rg`、`git diff`、`git log`、`git show`
- 读取日志、崩溃跟踪和配置
- 现有测试运行或最小安全重现命令

不要编辑文件、注入新的仪器或实现修复作为此技能的一部分。

## 步骤 3：并行启动四个只读调查员

当问题足够大或模糊到并行调查有帮助时启动四个子代理。对于微小且明显的问题，在本地调查是可以接受的。

对于每个子代理：

- 给出相同的错误数据包和调查简报
- 说明子代理是只读的
- 不要让子代理编辑文件、运行 `apply_patch`、暂存更改、提交或执行任何其他状态改变操作
- 仅要求简洁的调查输出
- 要求：假设、支持证据、缺失证据、最小证明步骤和置信度
- 告诉子代理避免泛型代码质量反馈、细节或没有证据的投机猜测
- 告诉子代理仅将发现发送回主代理

使用这四个调查角色。

### 子代理 1：重现和范围调查

澄清确切的故障形状及其边界。

检查：

1. 最狭隘的可靠触发器
2. 使错误出现或消失的条件
3. 故障边界处的预期与实际行为
4. 影响是本地的、跨越的、确定性的还是不稳定的

此子代理是只读的。它不得编辑文件、应用补丁或进行任何其他工作区更改。

推荐子代理角色：`reviewer`

### 子代理 2：代码路径和故障接缝调查

追踪最可能的执行路径并识别行为发生分歧的接缝。

检查：

1. 状态转换、生命周期边缘或顺序问题
2. 调用者和被调用者之间的不匹配假设
3. 数据流或控制流中断
4. 最可能负责故障的最小代码区域

此子代理是只读的。它不得编辑文件、应用补丁或进行任何其他工作区更改。

推荐子代理角色：`explorer` 用于广泛追踪，或 `reviewer` 当更强的本地推理传递更有用时

### 子代理 3：最近更改和回归调查

查找附近历史记录或更改的合同中可能的回归。

检查：

1. 与症状相关的最近 diff
2. 配置、标志、依赖项、架构或迁移漂移
3. 多个入口点应该一起更改的部分更新
4. 符合错误报告时间的行为更改

此子代理是只读的。它不得编辑文件、应用补丁或进行任何其他工作区更改。

推荐子代理角色：`reviewer`

### 子代理 4：证明计划和可观测性调查

确定确认或拒绝领先假设的最快方法。

检查：

1. 应该失败的最小现有测试或重现
2. 最有用的当前日志、跟踪、指标或断言
3. 可以快速提高信心的最小非改变命令
4. 缺失什么证据以及如何在没有广泛改变的情况下收集它

此子代理是只读的。它不得编辑文件、应用补丁或进行任何其他工作区更改。

推荐子代理角色：`reviewer`

仅报告物质上改进找到真正原因的几率的假设。最好返回两个有证据支持的理论，而不是六个模糊的猜测。

## 步骤 4：合成排名假设

主代理拥有合成。将子代理输出视为原始调查输入，而不是最终输出。

合并并排名假设：

- 合并重复
- 丢弃弱推测
- 优先考虑证据而非优雅
- 将可能的根本原因与仅仅贡献因素分开
- 仅在它们仍然合理时保留替代理论

将幸存的假设规范化为此形状：

1. 假设
2. 支持证据
3. 缺失或冲突证据
4. 最小证明步骤
5. 置信度：高、中或低

如果证据太弱不足以进行真正的排名，直接说出来并呈现领先的未决问题。

## 步骤 5：输出清晰的诊断路径

按此顺序呈现结果：

1. 最可能的根本原因
2. 合理的替代原因（如有）
3. 最快的证明步骤
4. 推荐的修复路径
5. 未决问题或阻碍

当修复尚不清楚时，建议下一个证明步骤，而不是假装诊断已完成。

在有帮助时，将操作分组为：

- `立即证明`
- `接下来修复`
- `稍后跟进`

不要将修复实现为此技能的一部分。输出是一个只读诊断，带有优先排序的前进路径。

## 示例

**用户请求：**

> 使用 @bug-hunt-swarm 调查此故障、证明根本原因、实现最小安全修复并进行验证。

## 限制

- 仅当任务清楚地符合其上游源和本地项目背景时才使用此技能。
- 在应用更改之前验证命令、生成的代码、依赖项、凭据和外部服务行为。
- 不要将示例视为特定于环境的测试、安全审查或用户批准破坏性或昂贵操作的替代。
