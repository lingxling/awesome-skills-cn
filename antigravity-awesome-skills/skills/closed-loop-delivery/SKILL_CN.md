# 闭合循环交付

## 概览

将每个任务视为不完整，直到验收标准在证据中得到验证，而不是仅仅改变代码。

核心规则：**根据 DoD（完成定义）交付，而不是根据代码差异大小交付。**

## 何时使用
在以下情况下使用此技能：
- 用户给出编码/修复任务并期望端到端完成
- 任务跨越代码 + 测试 + PR 注释 + 开发部署 + 运行时检查
- 应避免重复手动提示，如"现在测试"、"现在部署"、"现在重新检查 PR"

不使用此技能的情况：
- 纯 Q&A/解释
- 生产部署请求，没有明确的人工批准
- 因缺少无法推断的密钥/账户访问而阻止的任务

## 所需输入

在执行前，定义一次这些内容：
- 任务目标
- 验收标准 (DoD)
- 目标环境（默认 `dev`）
- 最大迭代轮数（默认 `2`）

如果缺少验收标准，请请求一次。如果用户不提供，建议一个具体的默认值并继续。

## 问题门槛依赖

在执行前，更倾向于使用 `create-issue-gate`。

- 如果问题状态是 `ready` 并且执行门是 `allowed`，继续。
- 如果问题状态是 `draft`，不要执行实现/部署/审查循环。
- 在开始执行前需要用户提供的、可测试的验收标准。

## 默认工作流

1. **定义 DoD**
   - 将请求转换为可测试的标准。
   - 示例：结账任务 DoD = "结账端点在开发中返回有效的、可打开的第三方支付 URL"。

2. **实现最小变更**
   - 将范围保持紧凑以实现任务目标。

3. **本地验证**
   - 首先运行专注测试，然后根据需要进行更广泛的检查。

4. **审查循环**
   - 获取 PR 注释/审查。
   - 分类有效与非可操作的。
   - 修复有效项，重新运行验证。

5. **开发部署 + 运行时验证**
   - 当运行时行为重要时部署到 `dev`。
   - 通过真实 API/Lambda/日志证据针对 DoD 进行验证。

6. **完成决定**
   - 仅在所有 DoD 检查通过时报告"完成"。
   - 否则继续循环直到通过或停止条件。

## PR 注释轮询策略

默认情况下避免嘈杂的短轮询。使用批处理窗口：

- **第 1 轮：** 等待 `3 分钟`，收集增量注释/审查
- **第 2 轮：** 等待 `6 分钟`，再次收集增量
- **最后一轮：** 等待 `10 分钟`，收集所有剩余可见注释/审查

在每一轮：
- 一次批处理所有新注释
- 避免在每个单个注释后立即重新轮询
- 在 `10 分钟` 轮后，停止等待并继续处理该点可见的所有注释

如果 CI 仍在运行，将轮询与检查完成边界对齐，而不是固定的快速轮询。

## 人工门槛规则 (必须询问)

需要为以下事项获得明确的用户确认：
- 生产/暂存部署超出商定范围
- 破坏性操作（历史重写、强制推送、数据破坏性操作）
- 涉及计费/安全态势变化的操作
- 存储库/运行时中不可用的密钥值
- 实质上改变结果的模糊 DoD

## 迭代/停止条件

在以下情况下停止并升级为简洁的阻塞报告：
- DoD 在最大轮数后仍然失败（默认 `2`）
- 外部依赖阻止进度（提供者中断、缺少凭据、账户权限）
- 冲突的审查指令无法同时满足

升级报告必须包括：
- 通过的内容
- 失败的内容
- 证据（命令/日志/API 结果）
- 用户所需的最小决定

## 输出合同

声称完成时，始终包括：
- 验收标准检查表，显示通过/失败
- 运行的命令/测试
- 运行时证据（端点/Lambda/日志关键行）
- PR 状态（新可操作注释计数）

不要在没有证据的情况下声称成功。

## 示例

**用户请求：**

> 从复现到根本原因证明、实现、测试、审查和最终验证处理此错误。

## 限制
- 仅在任务与上述范围匹配时使用此技能。
- 不要将输出视为特定于环境的验证、测试或专家审查的替代品。
- 如果需要的输入、权限、安全边界或成功标准缺失，请停止并寻求澄清。
