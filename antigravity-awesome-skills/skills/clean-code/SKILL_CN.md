# 清洁代码技能

此技能体现了 Robert C. Martin（Uncle Bob）《Clean Code》的原则。使用它将"可工作的代码"转变为"清洁的代码"。

## 🧠 核心理念
> "代码是清洁的，如果它可以被阅读，并由其原作者以外的开发者增强。" — Grady Booch

## 何时使用
在以下情况下使用此技能：
- **编写新代码**：从一开始就确保高质量。
- **审查 Pull Request**：提供有建设性的、基于原则的反馈。
- **重构遗留代码**：识别并移除代码异味。
- **改进团队标准**：对齐行业标准最佳实践。

## 1. 有意义的名称
- **使用意图明确的名称**：`elapsedTimeInDays` 而不是 `d`。
- **避免误导信息**：如果实际上是 `Map`，不要使用 `accountList`。
- **做出有意义的区分**：避免 `ProductData` 对 `ProductInfo`。
- **使用可读/可搜索的名称**：避免 `genymdhms`。
- **类名**：使用名词 (`Customer`, `WikiPage`)。避免 `Manager`, `Data`。
- **方法名**：使用动词 (`postPayment`, `deletePage`)。

## 2. 函数
- **小型函数！**: 函数应该比你想象的更短。
- **只做一件事**：函数应该只做一件事，并做好它。
- **单一抽象级别**：不要混合高级业务逻辑和低级细节（如正则表达式）。
- **描述性名称**：`isPasswordValid` 比 `check` 更好。
- **参数**：0 是理想的，1-2 还可以，3+ 需要非常强烈的理由。
- **无副作用**：函数不应该秘密改变全局状态。

## 3. 注释
- **不要注释坏代码—重写它**：大多数注释是无法用代码表达自己的失败标志。
- **用代码解释自己**：
  ```python
  # 检查员工是否有资格获得完整福利
  if employee.flags & HOURLY and employee.age > 65:
  ```
  vs
  ```python
  if employee.isEligibleForFullBenefits():
  ```
- **好的注释**：法律、信息性（正则表达式意图）、澄清（外部库）、TODOs。
- **坏的注释**：含糊、冗余、误导、强制、噪音、位置标记。

## 4. 格式化
- **报纸比喻**：高级概念在顶部，细节在底部。
- **垂直密度**：相关行应该彼此靠近。
- **距离**：变量应在其使用位置附近声明。
- **缩进**：对结构可读性至关重要。

## 5. 对象和数据结构
- **数据抽象**：在接口后隐藏实现。
- **Demeter 法则**：一个模块不应该知道它操纵的对象的内部结构。避免 `a.getB().getC().doSomething()`。
- **数据传输对象 (DTO)**：具有公共变量且没有函数的类。

## 6. 错误处理
- **使用异常而不是返回码**：保持逻辑清洁。
- **先写 Try-Catch-Finally**：定义操作的范围。
- **不要返回 Null**：它强制调用者每次都检查 null。
- **不要传递 Null**：导致 `NullPointerException`。

## 7. 单元测试
- **TDD 的三条法则**：
  1. 在有失败的单元测试之前，不要编写生产代码。
  2. 不要编写超过足以失败的单元测试。
  3. 不要编写超过足以通过失败测试的生产代码。
- **F.I.R.S.T. 原则**：快速、独立、可重复、自验证、及时。

## 8. 类
- **小型！**: 类应该有单一责任 (SRP)。
- **阶梯规则**：我们希望代码像自上而下的叙述一样读取。

## 9. 异味和启发式
- **刚性**：难以改变。
- **脆性**：在许多地方破裂。
- **不可移动性**：难以重用。
- **粘性**：难以做正确的事。
- **不必要的复杂性/重复**。

- [ ] 我是否传递了太多参数？
- [ ] 此更改是否有失败的测试？

## 限制
- 仅在任务与上述范围匹配时使用此技能。
- 不要将输出视为特定于环境的验证、测试或专家审查的替代品。
- 如果需要的输入、权限、安全边界或成功标准缺失，请停止并寻求澄清。
