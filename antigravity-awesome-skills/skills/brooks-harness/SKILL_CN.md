# brooks-lint — 维护工具（编排器）
## 何时使用

当你需要 brooks-lint 插件本身的维护编排器时使用此技能。运行顺序子代理管道 — 作者 → 评估 → QA → 触发审计 → 发布 — 添加或编辑技能、刷新评估套件、保持四个清单 + README + CHANGELOG + AGENTS/GEMINI 同步、审计触发...


此技能编排**brooks-lint 存储库本身**的工作。它运行顺序
子代理管道：每个阶段是在 `.claude/agents/` 中定义的专用代理。使用 `Agent` 工具生成每个代理，将 `subagent_type` 设置为代理名称，并**始终
设置 `model: "opus"`**。阶段按顺序相互依赖，因此这是管道，而不是
并行团队。

## 管道

```
[编排器]
   阶段 0  上下文检查
   阶段 1  分类请求 → 选择阶段
   阶段 2  按顺序运行所选阶段，带有 QA 循环回路：
            技能作者 → 评估策展人 → 一致性质量保证 ─(失败)→ 回到作者
                                              │ 通过
                                              ▼
                            触发边界审计员   （仅当描述更改时）
                                              ▼
                                      发布管理器  （仅当请求发布时）
   阶段 3  报告 + 收集反馈
```

## 阶段 0 — 上下文检查

在做任何事情前确定运行模式：

- `_workspace/brooks-harness/` 存在 + 维护者要求重做之前运行的一部分 →
  **部分重新运行**：仅调用受影响的阶段，重用之前的笔记。
- `_workspace/brooks-harness/` 存在 + 新请求 → **新运行**：将旧
  文件夹移到 `_workspace/brooks-harness_prev/`，全新开始。
- 没有 `_workspace/brooks-harness/` → **初始运行**：创建它。

运行笔记和 QA 报告位于 `_workspace/brooks-harness/`。**真正的**
工件是存储库文件本身 — 代理直接编辑 `skills/`、`evals/`、清单；`_workspace/` 仅保存运行的笔记和审计的通过/失败判决。

## 阶段 1 — 分类请求

选择最小的阶段集。QA 阶段**绝不跳过** — 每项更改都
受到管理。

| 请求 | 作者 | 评估 | QA | 触发审计 | 发布 |
|------|:----:|:----:|:--:|:-------:|:----:|
| 添加新技能 | ✓（通过 `new-skill` 脚手架） | ✓ | ✓ | ✓ | — |
| 编辑技能/指南内容 | ✓ | 如果代码更改 | ✓ | 如果 `description` 更改 | — |
| 编辑 `_shared/` 框架 | ✓ | 如果风险定义更改 | ✓ | — | — |
| 仅评估套件 | — | ✓ | ✓ | — | — |
| 修复触发描述 | ✓ | — | ✓ | ✓ | — |
| 发布 | — | — | ✓ | — | ✓ |
| 完整：更改 + 发布 | ✓ | 按需要 | ✓ | 如果适用 | ✓ |

## 阶段 2 — 运行管道

按顺序将每个选定的阶段作为子代理生成。向每个代理传递 (a) 任务
合同和 (b) 前一个阶段的摘要。代理将其摘要写入
`_workspace/brooks-harness/`；在阶段之间读取它们。

1. **技能作者** — 创建/编辑内容。对于全新技能，它调用
   `new-skill` 脚手架。返回接触的文件列表 + 约定相关的
   选择（新风险代码、新步骤编号、更改的 `description` 触发短语）。
2. **评估策展人** — 如果 `技能作者` 报告新/更改风险代码或模式，添加
   配对的快乐路径 + 误报场景并运行 `npm run evals`。
3. **一致性质量保证** *（门控 — 绝不跳过）* — 运行 `npm run validate` + `npm test` +
   `npm run evals`，然后是跨文档同步检查（清单、README 徽章、
   CHANGELOG、AGENTS/GEMINI 书籍计数、评估计数）。写入通过/失败判决。
   **失败时：循环回到判决中命名的代理（作者或评估策展人），
   修复，然后重新运行 QA。重复一次；如果仍然失败，停止并报告给
   维护者。**
4. **触发边界审计员** — 运行**仅当 `description` 字段更改时**。它
   对已发布技能的六个触发表面进行只读审计，以防虚假触发和
   路由冲突。呈现其发现；如果它标记真实冲突，循环回到
   技能作者。
5. **发布管理器** — 运行**仅当请求了发布时**，并且**仅在 QA
   通过后**。通过 `release` 技能切断发布。

## 阶段 3 — 报告和反馈

报告：运行的阶段、更改的文件、QA 判决、触发审计发现（如果有）和
发布 URL（如果有）。然后向维护者提供反馈机制："结果、代理角色或管道顺序中有什么需要调整吗？"在 CLAUDE.md 工具变更日志表中记录接受的更改。

## 此工具强制实施的约定

- **所有 `Agent` 调用使用 `model: "opus"`** — 工具质量追踪代理推理。
- **一致性质量保证必须是 `general-purpose`**（它运行 npm 脚本）；触发
  边界审计员是只读的。
- **不创建斜杠命令** — 短形式由
  会话启动钩子自动安装。
- **直接到主分支**：更改推送到 `main` 而无需 PR（根据存储库 CLAUDE.md）；全局
  简化 → 审查 → 提交门控仍适用于非文档编辑，但技能/指南
  内容是 markdown 并遵循验证门控。

## 错误处理

- 失败一次的阶段使用其错误作为输入重试一次；第二次失败
  停止管道并报告给维护者（没有静默跳过）。
- QA 失败绝不继续发布。
- 冲突数据报告时带有来源，不删除。
- 高风险 git 操作（`--no-verify`、`--force`、历史重写）需要显式
  维护者授权 — 发布管理器停止并要求。

## 测试场景

**正常流程 — "添加 brooks-security 技能"：**阶段 1 选择作者+评估+QA+审计。
技能作者运行 `new-skill brooks-security`，创建 SKILL.md（带有兄弟雕刻
"不要触发："条款）+ 指南；评估策展人添加 S 代码快乐路径 + 
误报场景；一致性质量保证运行门 → 通过；触发边界审计员
确认与 brooks-review/audit 无碰撞。报告列出文件 + 通过。

**错误流程 — 书籍计数漂移上的 QA 失败：**维护者添加第十三本书但
仅编辑 `source-coverage.md`。一致性质量保证的跨文档检查发现 README 仍
说"十二" → 失败，归因于技能作者。编排器循环回；技能作者
更新 README/AGENTS/GEMINI 措辞；QA 重新运行 → 通过。没有要求发布，因此
管道在阶段 3 结束。

## 限制

- 仅当任务清楚地符合其上游源和本地项目背景时才使用此技能。
- 在应用更改之前验证命令、生成的代码、依赖项、凭据和外部服务行为。
- 不要将示例视为特定于环境的测试、安全审查或用户批准破坏性或昂贵操作的替代。
