# 规范驱动循环

将不确定的软件请求转变为已批准的规范、受控的实现和有证据支持的验收。保持项目文档在存储库的既定位置；否则使用 `docs/spec-driven/<feature-slug>/`。

## 何时使用

使用此技能处理新产品、中大型功能、跨模块更改或需要 PRD/技术设计、主动澄清、多代理执行或主代理判断的请求。不要将其用于小型单文件更改、微小错误修复、代码解释、仅审查或诊断工作、纯研究或规范已完成的简单任务。

## 快速示例

```text
$spec-driven-loop 构建具有基于角色的访问和有证据支持的验收的多租户作业仪表板。
```

## 限制

- 不适用于小型隔离编辑、仅审查工作、诊断或纯研究。
- 不替代特定于环境的测试或授予不相关的更改或外部操作的授权。
- 生产实现在用户明确批准冻结的规范和验收合同前无法启动。

遵循存储库说明和整个授权边界。将生成的项目文档与用户的语言或存储库现有文档语言匹配；保持标识符 (如 `FR-001` 和 `AC-001`) 稳定。

## 操作不变量

- 事实是代理的责任。决策属于用户。
- 在提出问题前调查可发现的事实。仅询问真实的产品决策或重要的技术权衡。
- 在用户明确批准规范、范围和验收实现合同前，永远不要编写或修改生产代码。
- 永远不要隐瞒不确定性。将其标记为 `TBD`、`ASSUMPTION` 或 `BLOCKED`。
- 子代理的完成报告是证据，而非验收。主代理拥有集成和最终判断。
- 在并行工作前冻结共享接口、数据结构和公共类型。分配非重叠文件所有权；序列化重叠工作。
- 在每次决策或实现循环后更新持久文档。聊天记录不是真相的来源。
- 如果实现揭示需求变化而非代码缺陷，停止受影响的工作、修改规范、获取更新的用户批准，然后恢复。
- 保留用户的授权范围。规范批准授权已批准的实现，而非不相关的更改或外部操作。

需求审查阶段受 Matt Pocock 的 MIT 许可 `grill-me` / `grilling` 决策树和前沿方法启发。

## 文档边界

保持每个事实在一个权威文档中，并在其他地方参考其稳定 ID：

- `PRD.md`：为什么以及产品必须做什么；拥有范围、用户行为、业务规则、假设和产品决策。
- `TECH_DESIGN.md`：已批准的产品行为将如何工作；拥有架构、合同、数据、操作、安全和技术决策。
- `ACCEPTANCE.md`：可观察的证明冻结需求得到满足；拥有通过/失败标准和所需证据。
- `AGENT_PLAN.md`：谁执行已批准的实现工作；拥有依赖关系、文件所有权、验证和代理任务合同。
- `LOOP.md`：当前可恢复的执行状态和仅附加循环历史；拥有尝试、证据、判断、返工、风险和后续操作。

创建或更新这五个文档时阅读 [references/document-templates.md](references/document-templates.md)。在分配实现任务、集成代理工作、判断验收或发出返工前阅读 [references/agent-and-judge-contracts.md](references/agent-and-judge-contracts.md)。

## 1. 检查当前系统

在向用户提出问题前：

1. 阅读适用的 `AGENTS.md`、项目说明、现有规范和存储库约定。
2. 检查相关架构、模块、接口、数据库、测试、部署方法和代码约定。
3. 确定已建立的域术语和文档位置。
4. 从代码、文件、工具和文档解决事实。在草稿中记录发现和来源，而不是要求用户重新发现。
5. 区分产品选择和技术选择，并注意决策依赖关系。

如果冻结的、已批准的 PRD、技术设计和验收文档已存在，验证它们的状态、一致性和适用性。从规划或当前 `LOOP.md` 恢复，而非重复已解决的审查。如果缺少批准或请求更改冻结行为，返回到相应的规范阶段。

## 2. 起草 `PRD.md`

从请求和检查的系统创建最佳初始 PRD。包括：

- 问题和上下文；
- 用户和利益相关者；
- 产品目标和可测量的成功指标；
- 用户流；
- 具有稳定 ID 的功能需求 (`FR-001`、`FR-002`，...);
- 业务规则和数据生命周期；
- 范围内、范围外和非目标；
- 假设；
- 开放的产品决策；
- 决策日志。

不要将未知数转变为要求。标记每个未解决的项目为 `TBD`、`ASSUMPTION` 或 `BLOCKED`，并显示其影响的 FR。

## 3. 审查产品决策

将未解决的决策表示为依赖关系树。当前**前沿**仅包含上游决策已解决的高影响问题。

对于每一轮：

1. 选择一到三个用户现在可以回答的独立前沿问题。
2. 对于每个问题，说明为什么重要、具体选项、每个选项的影响、建议选项及理由。
3. 对不影响验收行为的低风险问题偏好可逆的明确假设。
4. 回答后，立即更新 `PRD.md` 及其决策日志，然后重新计算前沿。
5. 继续直到没有重要的未解决分支。不要转储依赖问题的积压或重复已解决的问题。

永远不要自动假设核心产品行为、数据所有权、权限或安全行为、迁移、外部兼容性、支付或金钱移动、破坏性操作、明确的性能目标或改变最终验收的行为。将这些保持为阻塞程序。

当产品前沿清晰时，总结确认的决策、已接受的假设、非目标、延期项和剩余风险。要求用户确认 PRD 反映共享的产品理解后，将其视为冻结。

## 4. 起草和审查 `TECH_DESIGN.md`

了解产品行为后，记录：

- 当前系统状态和总体方法；
- 模块边界和职责；
- 接口合同；
- 数据模型和迁移；
- 状态转变；
- 并发、一致性和幂等性；
- 身份验证、授权、隐私和安全；
- 故障、重试、恢复和降级；
- 性能和容量；
- 日志、指标和警报；
- 兼容性；
- 发布和回滚；
- 测试边界；
- 替代方案和技术决策日志；
- 受产品决策阻塞的技术问题。

当设计项目依赖于未解决的产品决策时，标记其为 `BLOCKED`。使用相同的决策树/前沿方法审查重要的技术选择：每轮一到三个可回答的问题、选项和影响、带有理由的建议、立即的文档更新和无隐藏的高风险假设。通过检查系统解决普通实现事实。

## 5. 冻结 `ACCEPTANCE.md` 并请求批准

在 PRD 和技术设计共享稳定理解后，编写验收合同。为每个标准给予稳定 ID (`AC-001`、`AC-002`，...)，将其链接到一个或多个 FR，并指定：

- 场景和前置条件；
- 操作或事件；
- 可观察的预期结果；
- 所需证据；
- 它是否是发布阻塞程序。

涵盖适用的成功路径、边界和无效输入、权限、故障和恢复、重复请求和幂等性、并发、兼容性、性能和容量、迁移、回滚、回归和现有质量门控。区分范围内、范围外、非目标、延期、假设、发布阻塞程序和完成定义。

不要接受主观标准，如"好的体验"、"好的性能"、"高代码质量"或"大部分工作"。每个阻塞 AC 都需要可观察的证据，如自动化测试、API 响应、数据库状态、日志、指标、屏幕截图、性能结果或精确的手动检查。

向用户显示简洁规范总结并询问：**规范、范围和验收条件已定义。您批准实现吗？** 记录答案。不要在明确批准前编写生产代码。

## 6. 创建 `AGENT_PLAN.md`

仅在实现批准后，将工作分割为独立可验证的竖片，而非机械地分离前端、后端和测试。对于每个任务包括：

- 任务 ID 和目标；
- 链接的 FR 和 AC ID；
- 输入和依赖关系；
- 确切允许的文件或目录；
- 确切禁止的文件或目录；
- 所需代码、测试或文档；
- 所需检查和证据；
- 停止和报告条件。

在并行委托前，冻结共享接口、模式和公共类型。确认写入不重叠。序列化任何具有重叠所有权或未解决依赖关系的任务。仅当至少两个任务真正独立且委托可用且已授权时才使用多个代理；不要仅为显示并行性而创建代理。

主代理维护规范、批准所有权变化、处理依赖关系和冲突、集成结果、运行系统级验证并判断最终验收。子代理不可扩展范围、更改验收标准、单方面更改共享合同、跨越所有权边界、降低测试要求或宣布整个项目完成。

## 7. 创建和维护 `LOOP.md`

在生产实现前创建 `LOOP.md`。其顶部部分必须公开足够的状态以便新会话在仅阅读顶部状态和当前循环后恢复。使用恰好一个当前状态：

`drafting`、`grilling`、`awaiting-spec-approval`、`ready`、`implementing`、`judging`、`changes-requested`、`blocked` 或 `accepted`。

每个循环记录其循环 ID、目标、FR/AC ID、分配、依赖关系、输出、更改的文件、命令/检查、结果、证据、主代理判断、失败条件、返工要求、未解决的风险、下一个状态和下一个操作。当现实变化时更新顶部状态。永远不要删除或覆盖失败的循环；追加下一个尝试。

## 8. 执行已批准的工作

仅给予每个子代理其任务合同所需的上下文。要求 [references/agent-and-judge-contracts.md](references/agent-and-judge-contracts.md) 中的完成报告格式。将合同偏差、新阻塞程序、接口更改和所有权冲突视为停止和报告事件。

按依赖关系顺序集成。检查实际更改而非依赖摘要。保持 `LOOP.md` 当前的文件、检查、结果、证据、风险和状态。

## 9. 独立判断

主代理必须：

1. 将实际 diff 和行为与冻结规范进行比较。
2. 检查所有权合规性和范围扩展。
3. 检查跨模块合同和数据结构。
4. 运行最高可行的端到端验证加必要的单元、集成和回归测试。
5. 执行适用的故障、权限、幂等性、并发、迁移、回滚和恢复行为。
6. 为每个阻塞 AC 生成证据。
7. 记录验收矩阵：`验收 ID | 结果 | 证据 | 缺陷/警告`。

允许的结论是 `ACCEPTED`、`CHANGES_REQUESTED`、`BLOCKED` 和 `ACCEPTED_WITH_CAVEATS`。缺少阻塞 AC 的证据是失败。现有代码、通过的单元测试、子代理的声明或多数同意本身永远不够；仅冻结的验收合同决定结果。

对于 `CHANGES_REQUESTED`，为仅失败的 AC 附加新循环，包括复现证据、约束最小修复范围并要求回归覆盖。永远不要削弱验收以制造通过。在同一 AC 在三个连续循环中失败判断后，停止自动返工并要求用户选择重新设计、范围变化、已接受限制或该部分终止。

## 10. 交付

首先呈现结果，然后报告完成的范围、不完整或延期的范围、验收矩阵、测试和验证证据、关键设计决策、剩余风险、已接受的假设和建议的后续步骤。确保最终 `LOOP.md` 状态与真实结果匹配。
