# 如果规范不足则询问问题

## 何时使用

当请求有多个合理的解释或关键详情（目标、范围、约束、环境或安全）不清楚时使用此技能。

## 何时不使用

当请求已经清楚或快速、低风险的发现读取可以回答缺失的详情时不使用此技能。

## 目标

提出回避错误工作所需的最少澄清问题集；在必需问题得到回答或用户明确批准带有说明的假设继续前不要开始实现。

## 工作流

### 1) 确定请求是否规范不足

在探索如何执行工作后，如果以下任何或所有都不清楚，将请求视为规范不足：
- 定义目标（应该改变什么与保持不变）
- 定义"完成"（接受标准、示例、边缘情况）
- 定义范围（哪些文件/组件/用户在内/外）
- 定义约束（兼容性、性能、风格、依赖、时间）
- 识别环境（语言/运行时版本、OS、构建/测试运行器）
- 澄清安全/可逆性（数据迁移、推出/回滚、风险）

如果存在多个合理的解释，假设它规范不足。

### 2) 首先询问必需问题（保持小）

在第一轮中提出 1-5 个问题。优先选择消除整个工作分支的问题。

让问题易于回答：
- 优化可扫描性（短的、编号的问题；避免段落）
- 尽可能提供多选选项
- 在适当时建议合理的默认值（将它们清楚地标记为默认/推荐选项；在列表中粗体推荐选项，或如果你在代码块中呈现选项，将粗体"推荐"行放在块之上并在块内标记默认值）
- 包含快速路径响应（例如，回复 `defaults` 接受所有推荐/默认选项）
- 当有帮助时包含低摩擦"不确定"选项（例如，"不确定 - 使用默认"）
- 如果这减少摩擦，将"需要知道"与"不错知道"分离
- 结构化选项使用户可以用紧凑决策回复（例如 `1b 2a 3c`）；以简洁语言重述所选选项以确认

### 3) 在行动前暂停

直到必需的答案到达：
- 不运行命令、编辑文件或产生取决于未知数的详细计划
- 仅执行清楚标记的、低风险的发现步骤（如果它不承诺你于方向）（例如检查代码库结构、读取相关配置文件）

如果用户明确要求你在没有答案的情况下继续：
- 将你的假设作为短编号列表声明
- 要求确认；仅在他们确认或更正后继续

### 4) 确认解释，然后继续

一旦你有答案，用 1-3 句话重述需求（包括关键约束和成功看起来像什么），然后开始工作。

## 问题模板

- "在我开始前，我需要：(1) ...、(2) ...、(3) .....。如果你不在乎 (2)，我将假设...."
- "这应该是哪一个？A) ... B) ... C) ...（选择一个）"
- "你会认为什么是'完成'？例如："
- "我必须遵循的任何约束（版本、性能、风格、依赖）？如果没有，我将针对现有项目默认值。"
- 使用编号问题与字母选项和清除回复格式

```text
1) 范围？
a) 最小改变（默认）
b) 在触及区域时重构
c) 不确定 - 使用默认

2) 兼容性目标？
a) 当前项目默认值（默认）
b) 也支持旧版本：<指定>
c) 不确定 - 使用默认

回复：defaults（或 1a 2a）
```

## 反模式

- 不要询问你可以用快速、低风险的发现读取回答的问题（例如配置、现有模式、文档）。
- 如果紧密的多选或是/否会更快消除歧义，不要询问开放式问题。

## 限制

- 仅当任务明确匹配上述范围时才使用此技能。
- 不要将输出视为环境特定验证、测试或专家审查的替代品。
- 如果缺少必需的输入、权限、安全边界或成功标准，请停止并要求澄清。
