# 智能体记忆纪律(Agent Memory Discipline)

## 概述

连接一个记忆工具并不会让智能体使用它:工具注册完成,会话正常运行,但什么都没有被回忆或保存。本技能补上了缺失的那部分——关于何时读取记忆、何时写入记忆的固定规则。

它解决的是一个具体的问题。一个可以使用记忆的智能体仍然会重复问已解决的问题、恢复已被纠正的习惯、在不同会话之间丢失决策,原因就在于没有任何东西告诉它何时该回忆、何时该保存。下面的规则让这两个时刻都变得明确。

## 何时使用本技能

- 当已经连接了某个记忆工具或 MCP 记忆服务器,但智能体并未持续使用它时。
- 当用户抱怨助手在不同会话之间丢失偏好、约定或过去的决策时。
- 当为某个项目搭建持久化记忆,智能体需要关于读写记忆的固定规则时。
- 当用户说"记住这个""我们之前决定了什么""回忆一下"或"把这个保存下来下次用"时。

## 工作原理

### 开始之前:任意记忆后端

智能体需要一个它可以调用的记忆工具。任何后端都可以,而规则对每一种都是一样的:

- **文件。** 一个由 Markdown 笔记组成的 `memory/` 文件夹,每个事实一个文件。无需依赖,完全可被 grep,可在 git 中版本化。
- **本地 MCP 记忆服务器。** 把所有内容都保留在本地机器上;有多种开源选择。
- **通过 MCP 提供的托管记忆服务。** 以数据存放在别处为代价,换取跨工具、跨机器的可移植性。

认证方式取决于所选后端的要求:本地文件夹不需要认证,本地 MCP 服务器使用其自身的配置,托管服务则需要 API 密钥或 OAuth 登录。本技能本身从不处理凭证,也绝不会把凭证写入记忆。

### 第一步:行动前先回忆

在做以下任何事情**之前**先读取记忆,而不是之后:

- 开始处理一个之前接触过的项目
- 选择某个库、模式或工具
- 编写测试、提交记录或文档,且这些场景存在适用的约定
- 回答"我们这里通常怎么做 X"
- 任何用户表述为"再来一次""像上次那样"或"按我们约定的"的事情

对于一次性的事实性问题、算术运算,或者当前消息中已经完全给出的内容,跳过回忆。回忆会消耗一次工具调用和上下文空间;把它花在一个自包含的问题上是浪费。

用用户实际使用的词汇加上项目或仓库名称进行搜索。如果第一次搜索没有返回有用结果,尝试一次范围更宽的查询,然后停止,不借助记忆继续推进,而不是反复循环搜索。

### 第二步:做出决策后保存

在以下任一情况刚发生时写入记忆:

- 做出了一个**决策**,并且下周仍然会有意义(例如"我们使用 pnpm""计费模块保持不动")
- 用户**纠正**了智能体,这是最强的保存信号
- 某种方案**失败**了,以及失败的原因
- 陈述了一个适用于本次任务之外的偏好
- 通过艰难的方式发现了关于环境的某个事实(端口、参数、必须保持运行的服务)

**不要**保存:可以再次读取的文件内容、对当前任务的重述、瞬时状态、用户标记为临时的任何内容,以及包含密钥、令牌或个人数据的任何内容。

一条记忆对应一个事实。一段包含四个决策的话,当其中一个发生变化时,无法被干净地替代。

### 第三步:写得让它能留存下去

一条三周后就毫无用处的记忆,就是写错了。为每条记录提供以下内容(如果后端没有对应字段,就写进正文):

- **是什么**:一句话说明决定了什么或观察到了什么
- **为什么**,简要说明,因为理由比决策本身更长久
- **何时**成为真,如果已不再成立,何时停止成立
- **来源**:某个文件、某次提交、某次对话、某次测试运行

优先使用用户的原话而不是转述。转述会产生偏差。

### 第四步:封存过去,而不是覆盖它

当某件事发生变化时,旧的记忆并没有错。它只是被**封存**了。

如果项目从 Redux 迁移到了 Zustand,那么"我们使用 Redux"在一月到六月之间是成立的。删除它会摧毁那段时间内每个组件编写方式的解释依据。标记为已被取代,保留其有效期窗口,并把新记录与之并列写入。

这是智能体记忆中最具破坏性的习惯,而且在有人问及旧代码之前,它一直是不可见的。

### 第五步:让矛盾保持可见

如果回忆返回了两条互相矛盾的记录,不要挑一条更接近的继续推进。把两条都呈现出来,附上日期,然后询问或标记出来。一条与近期失败相矛盾的约定,正是需要告知用户、而不是被含糊处理过去的情形。

### 第六步:对证据与政策区别权衡

- **证据**是发生过的事:一次运行、一次失败、一次观察。便宜、大量,但单条不可靠。
- **政策**是应该发生的事:一项约定、一个决策、一条规则。成本高,而且应该不容易被意外更改。

一次观察在以下情况下会升级为政策:当有人确认了它、当它被写入一份已合并的决策记录、或者当它反复成功过。在没有这些情况之一时,绝不要把单次观察提升为规则。

### 遵循本技能会产生什么

只有两件事,别无其他:

- **在工作开始前陈述出来的已回忆的上下文。** 相关的记录会连同其日期和来源一起被点出,让用户能看到智能体依赖的是什么。相互矛盾的记录会并列展示,而不是被合并。
- **决策、纠正和失败之后新增的记忆条目。** 每条一个事实,形式如下:

```text
Project uses pnpm, not npm. Stated by the user on 2026-08-11 after a lockfile conflict. Applies to all packages in this repo.
```

一条被取代的记录会保留原文,并获得一个结束日期和指向替代它的记录的指针。关于封存和证据示例的完整格式,见 [references/entry-format.md](references/entry-format.md)。

## 示例

### 示例 1:一次纠正

用户说: *"stop using npm here, we're on pnpm."*(别在这里用 npm 了,我们用的是 pnpm。)

1. 这是一次纠正,也是最强的保存信号。保存它。
2. 写入记录:

```text
Project uses pnpm, not npm. Stated by the user on 2026-08-11 after a lockfile conflict. Applies to all packages in this repo.
```

3. 不要同时保存"用户感到不满"、"运行了 npm install"或锁文件的内容。
4. 下一次会话中,在本仓库运行任何包管理命令之前,先进行回忆并找到这条记录。

### 示例 2:一次矛盾

回忆返回了两条记录:

```text
Integration tests run against the staging database (2026-06-02)
Integration tests use a local container; staging is off limits after the incident (2026-08-19)
```

1. 不要挑一条继续往下走。把两条都陈述出来,附上日期。
2. 询问: *"Memory has two rules for integration tests; the August one says staging is off limits. Use the local container?"*(记忆中对集成测试有两条规则;八月的那条说 staging 已被禁止使用。要用本地容器吗?)
3. 得到答复后,把不再成立的那条记录封存,标注结束日期,保留另一条。

### 示例 3:封存一条不再成立的记录

不要删除旧记录。为其添加结束日期和指向替代内容的指针,然后把新记录并列写入:

```text
[closed 2026-06-30, replaced by "State management uses Zustand"] State management uses Redux. Decided in the January architecture review.
State management uses Zustand. Migrated in June after the bundle size review. Applies to all new components.
```

## 最佳实践

- **要做:** 在涉及具体项目的工作前先回忆,并点出你依赖的记录及其日期和来源。
- **要做:** 在决策、纠正或失败发生后立即保存,一句话说明理由。
- **要做:** 保持每条记录只对应一个事实,以便之后的变化能被干净地取代。
- **要做:** 优先使用用户的原话而不是转述。
- **不要做:** 覆盖或删除一条已不再成立的记录;而是为它加上结束日期进行封存。
- **不要做:** 保存可以再次读取的文件内容、对当前任务的重述,或瞬时状态。
- **不要做:** 在没有人工确认、没有已合并的决策记录、也没有反复成功的情况下,把单次观察提升为规则。

## 局限性

- 本技能不安装任何记忆后端,也不需要账号。如果智能体没有可调用的记忆工具,它只能说明记忆不可用并继续执行。
- 它决定何时回忆以及保存什么内容。记录能否被再次找到,取决于后端自身的搜索能力。
- 它不会自行解决矛盾。它会把矛盾连同日期一起呈现出来,并询问用户哪一条成立。
- 用户要求移除某条记录后会发生什么,取决于后端支持的能力。
- 本技能不能替代针对特定环境的验证、测试或专家评审。
- 如果所需的输入、权限或安全边界缺失,应停下来寻求澄清。

## 安全与安全性说明

- 本技能不包含任何 shell 命令,也不会自行发起网络调用。它只通过用户已经连接好的记忆工具来读写记忆。
- 永远不要将密钥、令牌、密码或个人数据保存到记忆中,也绝不要把凭证写入记录。
- 托管记忆后端会把记录存储在本地机器之外。选择后端时请考虑这一点。
- 当用户要求移除某条记录时,按后端允许的方式将其封存或移除,并确认被移除的内容。

## 常见陷阱

- **问题:** 记忆工具不可用或出现故障。
  **解决方法:** 不借助记忆继续执行,用一句话说明情况,不要进入循环重试。工具恢复后立即保存那个待定的决策,而不是直接放弃它。
- **问题:** 回忆没有返回任何结果。
  **解决方法:** 运行一次范围更宽的查询,然后不借助记忆继续执行。空结果本身就是信息:说明这个主题是新的,因此此刻做出的决策值得被保存。
- **问题:** 回忆返回的内容太多。
  **解决方法:** 保留与当前项目和任务相匹配的记录;忽略其余的,而不是把它们全部塞进上下文。
- **问题:** 两条记录相互矛盾。
  **解决方法:** 把两条都展示出来并附上日期,然后询问哪一条成立。不要默默地解决冲突。
- **问题:** 某次保存被后端拒绝或过滤掉了。
  **解决方法:** 报告一次即可。不要反复换种说法去尝试让同一个事实通过。
