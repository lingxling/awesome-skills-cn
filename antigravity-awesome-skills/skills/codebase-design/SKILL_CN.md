# 代码库设计

## 何时使用

当此工作流与用户请求匹配时使用：用于设计深模块的共享词汇。当用户想要设计或改进模块的接口、发现深化机会、决定接缝放在哪里、使代码更可测试或 AI 可导航，或当另一个技能需要深模块词汇时使用。


_来源：[mattpocock/skills](https://github.com/mattpocock/skills) (MIT)._

设计**深模块**：在小接口后面有大量行为，放在干净的接缝处，通过该接口可测试。在设计或重组代码的任何地方使用此语言和这些原则。目的是为调用方提供杠杆、为维护者提供本地性以及为所有人提供可测试性。

## 术语表

准确使用这些术语 — 不要用"组件"、"服务"、"API"或"边界"替换。一致的语言是重点。

**模块** — 任何带有接口和实现的东西。故意为规模不可知的：函数、类、包或跨层切片。_避免_：单元、组件、服务。

**接口** — 调用方必须知道的所有内容才能正确使用模块：类型签名，但也包括不变量、排序约束、错误模式、所需配置和性能特征。_避免_：API、签名（太窄 — 它们仅指类型级表面）。

**实现** — 模块内部的内容、代码体。与**适配器**不同：一个东西可以是一个小适配器，有一个大实现（Postgres repo）或一个大适配器，有一个小实现（内存中的假对象）。当接缝是主题时使用"适配器"；否则使用"实现"。

**深度** — 接口处的杠杆：调用方（或测试）可以每单位接口进行行使的行为量，他们必须学习。当大量行为位于小接口后面时，模块是**深**的；当接口几乎与实现一样复杂时，模块是**浅**的。

**接缝** _（Michael Feathers）_ — 可以在不在该处编辑的地方改变行为的地方；模块接口所在的*位置*。接缝放在哪里是它自己的设计决定，与它后面的内容不同。_避免_：边界（用 DDD 的有界上下文重载）。

**适配器** — 满足接缝处接口的具体东西。描述*角色*（它填充什么槽），而不是实质（里面是什么）。

**杠杆** — 调用方从深度获得的：每单位接口他们学习的能力更多。一个实现在 N 个调用站点和 M 个测试中支付。

**本地性** — 维护者从深度获得的：更改、bug、知识和验证集中在一个地方，而不是分散在调用方中。一次修复，处处修复。

## 深 vs 浅

**深模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│   小接口           │  ← 几个方法，简单参数
├─────────────────────┤
│                     │
│  深度实现           │  ← 复杂逻辑隐藏
│                     │
└─────────────────────┘
```

**浅模块** = 大接口 + 少量实现（避免）：

```
┌─────────────────────────────────┐
│       大接口                    │  ← 许多方法，复杂参数
├─────────────────────────────────┤
│  薄实现                         │  ← 只是传递
└─────────────────────────────────┘
```

设计接口时，问自己：

- 我能减少方法的数量吗？
- 我能简化参数吗？
- 我能在内部隐藏更多的复杂性吗？

## 原则

- **深度是接口的属性，不是实现的属性。** 深模块在内部可以由小的、可模拟的、可交换的部分组成 — 它们只是不是接口的一部分。模块可以有**内部接缝**（对其实现私有，由其自己的测试使用）以及其接口处的**外部接缝**。
- **删除测试。** 想象删除模块。如果复杂性消失，它是直通的。如果复杂性在 N 个调用方中重新出现，它正在赢得它的保留。
- **接口是测试表面。** 调用方和测试跨越相同的接缝。如果您想测试*超过*接口，模块可能是错误的形状。
- **一个适配器意味着一个假设的接缝。两个适配器意味着一个真实的。** 除非某个东西实际上跨越它而变化，否则不要引入接缝。

## 为可测试性设计

好的接口使测试自然：

1. **接受依赖项，不要创建它们。**

   ```typescript
   // 可测试的
   function processOrder(order, paymentGateway) {}

   // 很难测试
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要产生副作用。**

   ```typescript
   // 可测试的
   function calculateDiscount(cart): Discount {}

   // 很难测试
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **小表面积。** 更少的方法 = 更少需要的测试。更少的参数 = 更简单的测试设置。

## 关系

- 一个**模块**恰好有一个**接口**（它呈现给调用方和测试的表面）。
- **深度**是**模块**的属性，根据其**接口**测量。
- **接缝**是**模块**的**接口**所在的地方。
- **适配器**位于**接缝**处并满足**接口**。
- **深度**为调用方产生**杠杆**，为维护者产生**本地性**。

## 拒绝的框架

- **深度为实现行数与接口行数的比率**（Ousterhout）：奖励填充实现。我们改为使用深度作为杠杆。
- **"接口"作为 TypeScript `interface` 关键字或类的公共方法**：太窄 — 这里的接口包括调用方必须知道的每个事实。
- **"边界"**：用 DDD 的有界上下文重载。说**接缝**或**接口**。

## 深入探讨

- **给定其依赖项深化一个集群** — 见 [DEEPENING.md](DEEPENING.md)：依赖项类别、接缝规则和替换而不是分层测试。
- **探索替代接口** — 见 [DESIGN-IT-TWICE.md](DESIGN-IT-TWICE.md)：启动并行子代理以几种根本不同的方式设计接口，然后在深度、本地性和接缝放置上进行比较。
