# 系统化调试
## 何时使用

当您需要具有根本原因分析的四阶段调试方法论时，使用此技能。在调查 bug、修复测试失败或排除故障时使用。强调先进行根本原因分析，再进行修复。


## 核心原则

**先进行根本原因调查，再进行修复。**

永远不要应用遮盖潜在问题的症状修复。在尝试修复之前，要理解出现问题的原因。

## 四阶段框架

### 第一阶段：根本原因调查

在修改任何代码之前：

1. **彻底阅读错误消息** - 每个单词都很重要
2. **一致地重现问题** - 如果不能重现它，就无法验证修复
3. **检查最近的更改** - 在这个开始失败之前改变了什么？
4. **收集诊断证据** - 日志、堆栈跟踪、状态转储
5. **追踪数据流** - 跟踪调用链以找到坏值的来源

**根本原因追踪技术：**
```
1. 观察症状 - 错误在哪里表现？
2. 找到直接原因 - 哪个代码直接产生错误？
3. 问"什么调用了这个？" - 向上映射调用链
4. 继续追踪 - 通过堆栈向后追踪无效数据
5. 找到原始触发器 - 问题实际上从哪里开始的？
```

**关键原则：**永远不要仅在错误出现的地方修复问题 — 始终追踪到原始触发器。

### 第二阶段：模式分析

1. **定位工作示例** - 查找类似的、工作正常的代码
2. **完全比较实现** - 不要只是浏览
3. **识别差异** - 工作正常的和损坏的代码有什么区别？
4. **理解依赖关系** - 这个代码依赖什么？

### 第三阶段：假设和测试

应用科学方法：

1. **制定一个明确的假设** - "错误出现是因为 X"
2. **设计最小测试** - 一次改变一个变量
3. **预测结果** - 如果假设正确，应该发生什么？
4. **运行测试** - 执行并观察
5. **验证结果** - 它是否如预测那样表现？
6. **迭代或继续** - 如果错了则重新制定假设，如果对了则实现

### 第四阶段：实现

1. **创建失败的测试用例** - 捕获 bug 行为
2. **实现单个修复** - 解决根本原因，而不是症状
3. **验证测试通过** - 确认修复有效
4. **运行完整测试套件** - 确保没有回归
5. **如果修复失败，停止** - 重新评估假设

**关键规则：**如果连续三次或更多修复失败，停止。这表明存在需要讨论的架构问题，而不是更多补丁。

## 红旗 - 流程违规

如果您发现自己这样想，立即停止：

- "先快速修复，稍后调查"
- "再试一次修复"（在多次失败后）
- "这应该行得通"（不理解为什么）
- "让我试试..."（没有假设）
- "在我的机器上能工作"（不调查差异）

## 更深层问题的警告信号

**连续修复在不同区域揭示新问题**表明存在架构问题：

- 停止打补丁
- 记录您发现的内容
- 在继续之前与团队讨论
- 考虑设计是否需要重新思考

## 常见调试场景

### 测试失败

```
1. 阅读完整的错误消息和堆栈跟踪
2. 识别哪个断言失败以及为什么
3. 检查测试设置 - 测试环境是否正确？
4. 检查测试数据 - 模拟/固定装置是否正确？
5. 追踪到意外值的源
```

### 运行时错误

```
1. 捕获完整的堆栈跟踪
2. 识别抛出的行
3. 检查哪些值是未定义/空值
4. 向后追踪以查找坏值的原始来源
5. 在源处添加验证
```

### "它之前能工作"

```
1. 使用 git bisect 找到破坏的提交
2. 将更改与之前的工作版本进行比较
3. 识别哪个假设发生了变化
4. 在假设违规的源处修复
```

### 间歇性故障

```
1. 查找竞态条件
2. 检查共享的可变状态
3. 检查异步操作排序
4. 查找时序依赖性
5. 添加确定性等待或适当的同步
```

## 调试清单

在声称 bug 已修复之前：

- [ ] 已识别并记录根本原因
- [ ] 已制定并测试假设
- [ ] 修复解决根本原因，而不是症状
- [ ] 创建了重现 bug 的失败测试
- [ ] 测试现在通过修复
- [ ] 完整测试套件通过
- [ ] 没有使用"快速修复"理由
- [ ] 修复最小且集中

## 成功指标

系统化调试实现了约 95% 的一次性修复率，而临时方法只有约 40%。

您做得对的迹象：
- 修复不会创建新 bug
- 您可以解释为什么会出现 bug
- 类似的 bug 不会重复出现
- 修复后代码更好，而不仅仅是"能工作"

## 与其他技能的集成

- **testing-patterns**：在修复之前创建重现 bug 的测试

## 限制

- 仅当任务清晰地匹配其上游源和本地项目上下文时，才使用此技能。
- 在应用更改之前，验证命令、生成的代码、依赖项、凭证和外部服务行为。
- 不要将示例作为环境特定测试、安全审查或用户对破坏性或成本高昂操作的批准的替代品。
