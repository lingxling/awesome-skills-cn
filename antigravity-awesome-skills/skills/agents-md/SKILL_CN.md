# 基于仓库证据维护 AGENTS.md

## 概述

创建或改进智能体指令,帮助编码智能体正确地修改仓库,而不必重新摸索其工作流程。每一条仓库专属的命令、路径和规则都要以当前工作区中的证据为依据。

优先做有针对性的差异化修改,而不是整体重写。没有放之四海而皆准的行数限制、必需的章节清单、符号链接布局,或提交归属策略;一切都应遵循该仓库自身的需求和维护者的意图。

## 何时使用

- 用户要求创建、更新、精简或审计 `AGENTS.md`。
- 一个 monorepo 需要根级指令,外加更细粒度的、针对各个包的覆盖规则。
- 现有的智能体指令含有过时的命令、重复的策略,或未经证实的声称。
- 用户想要将 `AGENTS.md` 与 `CLAUDE.md`、`.github/copilot-instructions.md` 或其他仓库指令文件进行协调统一。

当任务明确需要 `@agents-generator` 其打包好的生成模式、素材资源或备份工作流时,使用那个技能。当以可读性强、以证据为先的编辑为主要目标时,使用此技能。

## 工作原理

### 1. 保留现有意图

在写入之前,先阅读适用于目标路径的每一份指令文件,包括现有的 `AGENTS.md` 文件,以及相关的工具专属文件,如 `CLAUDE.md`、`GEMINI.md`、`.github/copilot-instructions.md` 和 `.github/instructions/*.instructions.md`。

- 尽可能原地改进现有的 `AGENTS.md`。
- 保留准确的、由维护者撰写的规则和仓库专属策略。
- 除非用户要求且仓库证据表明确实需要完全相同的内容,否则不要用符号链接替换另一个工具的指令文件。
- 不要在相互冲突的指令之间悄悄做出选择。遵循优先级更高的适用规则,或者在无法从仓库中确定预期策略时提出询问。

### 2. 构建一个有边界的证据地图

只检查足够了解工作实际如何完成的那部分仓库内容:

1. 阅读项目概述和贡献指南,例如 `README*`、`CONTRIBUTING*` 以及相关文档。
2. 阅读清单文件、锁文件、工作区文件、任务运行器和构建配置,以确定受支持的工具和确切的命令。
3. 阅读 CI 工作流以了解必需的检查。不要假设每一个 CI 或部署任务在本地运行都是安全或合适的。
4. 检查有代表性的源码和测试文件,了解命名、布局和测试约定。
5. 识别生成文件、迁移脚本、第三方引入的代码、大型测试夹具、密钥边界,以及仅限生产环境的操作。

在可用时优先使用 `rg --files` 和 `rg` 进行发现。追踪每一条非显而易见的命令或规则的来源,以免未经证实的说法进入最终文件。

### 3. 选择指令的作用范围

对于仓库范围的指导,使用根级 `AGENTS.md`。只有当某个子树在命令、架构、约定或安全边界上存在实质性差异时,才新增或修订一份嵌套的 `AGENTS.md`。

将共享规则保留在根级,嵌套文件中只放差异部分。对于实现了公开 AGENTS.md 约定的工具,目录树中最近的那个文件控制着其所在的工作子树。不要把完整的根文件复制到每一个包中。

### 4. 撰写高信号的指导内容

选择契合该仓库的标题,而不是强行套用固定模板。只有在有证据支持时才包含以下内容:

- **仓库地图:** 智能体必须了解的少数几个目录和边界。
- **安装与命令:** 确切的安装、开发、构建、lint、类型检查和测试命令,并在工作目录不显而易见时予以说明。
- **有针对性的验证:** 针对小改动的定向检查,以及交付前要求的更广泛检查。
- **变更规则:** 生成文件的归属、迁移、schema、API、依赖,以及跨包协调。
- **安全边界:** 密钥、生产数据、破坏性命令、部署,以及需要明确授权的操作。
- **贡献规则:** 影响实现或交付的、仓库专属的命名、格式化、提交或 Pull Request 要求。

撰写直接、可验证的陈述。优先采用:

```markdown
- 从仓库根目录运行 `npm test -- path/to/file.test.ts` 执行针对性测试。
```

而不是:

```markdown
- 确保测试通过并遵循最佳实践。
```

链接到已维护的文档,而不是复制它。将必需的检查与可选的、缓慢的、特权的或仅用于部署的检查区分开来。

### 5. 交付前进行验证

1. 完整重新阅读每一份已更改的 `AGENTS.md`。
2. 移除矛盾之处、重复规则、占位符和过时的声称。
3. 确认提到的每一个文件和目录都确实存在。
4. 将命令与清单文件或 CI 进行交叉检查,并在有用时运行安全、适度的检查。
5. 如果嵌套文件发生了变化,确认每一个文件只包含子树专属的规则,且不会与根文件产生意外冲突。
6. 以维护者的视角审视这份差异:新增的每一行都应该能改变智能体的决策,或预防一个真实可能发生的错误。

报告已更改的文件、使用的证据、实际运行过的检查,以及尚未解决的不确定性。绝不能说某条命令"经过测试",如果它只是从配置中读取出来的。

## 示例

### 创建一份有针对性的根级文件

发现的证据:

- `package-lock.json` 表明使用 npm。
- `package.json` 定义了 `lint`、`typecheck` 和 `test` 脚本。
- CI 从仓库根目录运行这三项检查。
- `src/generated/` 由 `npm run generate` 生成。

一个有用的结果可能包括:

```markdown
# Agent instructions

## Commands
- Run commands from the repository root.
- Install with `npm ci`.
- For handoff, run `npm run lint`, `npm run typecheck`, and `npm test`.

## Generated code
- Do not edit `src/generated/` directly; update its source and run `npm run generate`.
```

不要添加证据未能证实的包管理器、命令或生成文件规则。

### 修订而不抹除既有策略

如果现有文件有准确的发布限制,但测试命令已过时,只修改过时的命令以及受其直接影响的说明。即使更简短的替代版本看起来更干净,也要保留发布限制。

## 最佳实践

- 保持指令简洁到足以快速浏览,但让仓库的复杂度决定篇幅长短。
- 优先选择仓库专属的决策,而非泛泛的工程建议。
- 当项目支持针对性命令时予以包含;不要为只支持套件级运行的工具凭空发明文件级调用方式。
- 说明命令在哪里运行,以及是否会修改文件。
- 引用格式化工具和 linter 的配置,而不是重述每一条规则。
- 当语义不同时,让工具专属文件起到增补作用;不要假设所有智能体对格式或优先级的解读都相同。

## 安全与安全注意事项

- 将此视为会改变状态的技能,因为它可能编辑仓库文件。在交付前审查差异。
- 绝不要在智能体指令中包含密钥、凭据、内部 URL、个人数据或本地环境值。
- 不要仅为验证文档而运行部署、发布、数据库变更、历史重写或其他有实质后果的命令。
- 保留仓库策略中已有的审批关卡。
- 不要将私有仓库的指令上传给第三方服务。在向外部传输任何仓库内容之前,需先征得明确同意。

## 常见陷阱

- **猜测命令:** 从清单文件和 CI 中推断工具,而不是凭流行度猜测。
- **强行套用单一布局:** 一个符号链接或固定的章节清单可能抹除工具专属或维护者撰写的指导。
- **覆盖现有文件:** 做出证据支撑的最小改动。
- **复制 README:** 只包含会改变智能体行为的信息。
- **重复嵌套文件:** 共享指导保留在根级,局部差异放在相关代码附近。
- **声称进行了未实际运行的验证:** 在交付说明中区分"检查过"和"实际运行过"。

## 局限性

- 仓库证据可能不完整或相互矛盾;当某个重要的策略选择无法安全确定时,应主动询问。
- 一条已记录的命令仍可能需要在本地不可用的凭据、服务或操作系统支持。
- AGENTS.md 的支持程度和优先级在不同编码工具之间存在差异;当互操作性很重要时,请核实目标工具。
- 此技能能提升指令质量,但无法证明未来的每一个智能体都会正确遵循该文件。
