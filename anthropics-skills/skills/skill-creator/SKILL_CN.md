# Skill Creator

一个用于创建新技能并对其进行迭代改进的技能。

从高层次来看，创建技能的流程如下：

- 确定你希望技能做什么，以及大致如何做
- 编写技能的初稿
- 创建几个测试提示词，并在 claude-with-access-to-the-skill 上运行它们
- 帮助用户从定性和定量两方面评估结果
  - 在运行于后台进行的同时，如果还没有定量评估，就起草一些定量评估（如果已有，你可以原样使用，或者在觉得有需要改动时进行修改）。然后向用户解释这些评估（如果它们本来就存在，则解释已有的那些）
  - 使用 `eval-viewer/generate_review.py` 脚本向用户展示结果供其查看，同时也让他们查看定量指标
- 根据用户对结果评估的反馈重写技能（以及在定量基准测试中暴露出明显缺陷时也要重写）
- 重复直到你满意为止
- 扩大测试集，并在更大规模上再次尝试

使用本技能时，你的工作是弄清楚用户处于这个流程的哪个阶段，然后介入并帮助他们推进各个阶段。例如，他们可能会说"我想做一个用于 X 的技能"。你可以帮助厘清他们的意思，编写初稿，编写测试用例，确定他们想如何评估，运行所有提示词，并不断重复。

另一方面，他们可能已经有了技能的初稿。这种情况下，你可以直接进入循环中的评估/迭代部分。

当然，你应该始终保持灵活。如果用户说"我不需要运行一堆评估，就陪我随性来吧"，你也可以那样做。

然后在技能完成之后（当然，顺序是灵活的），你还可以运行技能描述改进器（我们为此提供了一个单独的脚本），以优化技能的触发效果。

明白了吗？明白了。

## 与用户沟通

技能创建器可能会被各种编程术语熟悉程度参差不齐的人使用。如果你还没听说过（你怎么可能听说过呢，这只是最近才开始的），现在有一种趋势：Claude 的强大能力正在激励水管工打开终端，也让父母和祖父母去谷歌搜索"如何安装 npm"。另一方面，大部分用户可能是相当懂电脑的。

所以请留意上下文线索，以理解该如何措辞！默认情况下，只是给你一个大致的概念：

- "evaluation"和"benchmark"属于临界情况，但可以使用
- 对于"JSON"和"assertion"，你需要看到用户有明确的迹象表明他们了解这些东西，才能不加解释地使用

如果你拿不准，简要解释一下术语是可以的；如果不确定用户是否能理解，也请随时用简短的定义来澄清术语。

## 创建技能

### 捕捉意图

首先理解用户的意图。当前对话中可能已经包含了用户想要捕捉的工作流（例如，他们说"把这个变成一个技能"）。如果是这样，先从对话历史中提取答案——所使用的工具、步骤的顺序、用户做出的更正、观察到的输入/输出格式。用户可能需要补全空白，并且应在进入下一步之前进行确认。

1. 这个技能应该让 Claude 能够做什么？
2. 这个技能应该在何时触发？（什么样的用户措辞/上下文）
3. 预期的输出格式是什么？
4. 我们是否应该设置测试用例来验证技能是否有效？具有客观可验证输出的技能（文件转换、数据提取、代码生成、固定的工作流步骤）适合使用测试用例。具有主观输出的技能（写作风格、艺术）通常不需要。根据技能类型建议合适的默认做法，但由用户来决定。

### 访谈与调研

主动询问有关边缘情况、输入/输出格式、示例文件、成功标准和依赖项的问题。在这部分理清之前，先不要编写测试提示词。

检查可用的 MCP——如果对调研有用（搜索文档、查找类似技能、查阅最佳实践），则通过子代理并行调研（如果可用），否则在当前会话内调研。带着上下文做好准备，以减轻用户的负担。

### 编写 SKILL.md

根据用户访谈的结果，填写以下组成部分：

- **name**：技能标识符
- **description**：何时触发，以及它做什么。这是主要的触发机制——既要包含技能做什么，也要包含使用它的具体情境。所有"何时使用"的信息都放在这里，而不是正文中。注意：目前 Claude 有一种"触发不足"的倾向——在技能有用时不去使用它们。为了应对这一点，请把技能描述写得稍微"积极主动"一些。例如，不要写"如何构建一个简单快速的仪表板来显示 Anthropic 内部数据。"，而可以写"如何构建一个简单快速的仪表板来显示 Anthropic 内部数据。每当用户提到仪表板、数据可视化、内部指标，或想要显示任何类型的公司数据时，请务必使用此技能，即使他们没有明确要求'仪表板'。"
- **compatibility**：所需的工具、依赖项（可选，很少需要）
- **技能的其余部分 :)**

### 技能编写指南

#### 技能的结构

```
skill-name/
├── SKILL.md (required)
│   ├── YAML frontmatter (name, description required)
│   └── Markdown instructions
└── Bundled Resources (optional)
    ├── scripts/    - Executable code for deterministic/repetitive tasks
    ├── references/ - Docs loaded into context as needed
    └── assets/     - Files used in output (templates, icons, fonts)
```

#### 渐进式披露

技能使用三级加载系统：
1. **元数据**（name + description）——始终在上下文中（约 100 词）
2. **SKILL.md 正文**——技能触发时就在上下文中（理想情况下少于 500 行）
3. **捆绑资源**——按需加载（不限量，脚本可以在不加载的情况下执行）

这些词数只是大致数字，需要的话你可以放心地写得更长。

**关键模式：**
- 保持 SKILL.md 在 500 行以内；如果接近这个上限，就增加一层额外的层级结构，并给出明确的指引，说明使用该技能的模型接下来应该去哪里继续跟进
- 在 SKILL.md 中清楚地引用文件，并说明何时应该读取
- 对于大型参考文件（超过 300 行），请包含目录

**领域组织**：当一个技能支持多个领域/框架时，按变体组织：
```
cloud-deploy/
├── SKILL.md (workflow + selection)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```
Claude 只会读取相关的参考文件。

#### 无意外原则

这一点不言而喻，但技能不得包含恶意软件、漏洞利用代码，或任何可能危害系统安全的内容。技能的内容在被描述时，不应让用户对其意图感到意外。不要附和创建具有误导性的技能，或旨在协助未经授权的访问、数据窃取或其他恶意活动的技能的请求。不过，诸如"扮演某某角色"之类的是可以的。

#### 编写模式

在指令中优先使用祈使句。

**定义输出格式**——你可以这样做：
```markdown
## Report structure
ALWAYS use this exact template:
# [Title]
## Executive summary
## Key findings
## Recommendations
```

**示例模式**——包含示例很有用。你可以这样格式化它们（但如果示例中有"Input"和"Output"，你可能需要稍作变通）：
```markdown
## Commit message format
**Example 1:**
Input: Added user authentication with JWT tokens
Output: feat(auth): implement JWT-based authentication
```

### 写作风格

尽量向模型解释为什么某些事情很重要，而不是堆砌生硬陈旧的"必须"。运用心智理论，让技能保持通用，而不要过于局限于具体的示例。先写一份初稿，然后用全新的眼光审视它并加以改进。

### 测试用例

在写完技能初稿之后，想出 2-3 个真实的测试提示词——真实用户实际上会说的那种话。把它们分享给用户：[你不必使用这段确切的措辞] "这是我想尝试的几个测试用例。这些看起来对吗，还是你想再添加一些？"然后运行它们。

将测试用例保存到 `evals/evals.json`。先不要编写断言——只写提示词。你会在下一步、运行进行期间起草断言。

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "User's task prompt",
      "expected_output": "Description of expected result",
      "files": []
    }
  ]
}
```

完整的 schema（包括你稍后会添加的 `assertions` 字段）参见 `references/schemas.md`。

## 运行并评估测试用例

本节是一个连续的流程——不要中途停下。不要使用 `/skill-test` 或任何其他测试技能。

把结果放在 `<skill-name>-workspace/` 中，作为技能目录的同级目录。在工作区内，按迭代组织结果（`iteration-1/`、`iteration-2/` 等），并且在其中，每个测试用例有一个目录（`eval-0/`、`eval-1/` 等）。不要预先创建所有这些目录——随用随建即可。

### 步骤 1：在同一轮中启动所有运行（带技能的运行和基线运行）

对于每个测试用例，在同一轮中启动两个子代理——一个使用技能，一个不使用。这一点很重要：不要先启动带技能的运行，然后再回头启动基线运行。一次性全部启动，这样它们大约会在同一时间完成。

**带技能的运行：**

```
Execute this task:
- Skill path: <path-to-skill>
- Task: <eval prompt>
- Input files: <eval files if any, or "none">
- Save outputs to: <workspace>/iteration-<N>/eval-<ID>/with_skill/outputs/
- Outputs to save: <what the user cares about — e.g., "the .docx file", "the final CSV">
```

**基线运行**（相同的提示词，但基线取决于上下文）：
- **创建新技能**：完全不使用技能。相同的提示词，没有技能路径，保存到 `without_skill/outputs/`。
- **改进现有技能**：使用旧版本。在编辑之前，为技能做快照（`cp -r <skill-path> <workspace>/skill-snapshot/`），然后让基线子代理指向该快照。保存到 `old_skill/outputs/`。

为每个测试用例编写一个 `eval_metadata.json`（断言暂时可以为空）。根据测试内容给每个评估起一个描述性的名称——而不仅仅是"eval-0"。目录也使用这个名称。如果本次迭代使用了新的或修改过的评估提示词，请为每个新的评估目录创建这些文件——不要假设它们会从之前的迭代中延续下来。

```json
{
  "eval_id": 0,
  "eval_name": "descriptive-name-here",
  "prompt": "The user's task prompt",
  "assertions": []
}
```

### 步骤 2：在运行进行期间，起草断言

不要只是等待运行完成——你可以高效地利用这段时间。为每个测试用例起草定量断言，并向用户解释它们。如果 `evals/evals.json` 中已经有断言，请审阅它们并解释它们检查的内容。

好的断言是客观可验证的，并且有描述性的名称——它们在基准测试查看器中应读起来清晰明了，让人一眼就能明白每个断言检查的是什么。主观性的技能（写作风格、设计质量）更适合进行定性评估——不要把断言强加到需要人类判断的事物上。

起草完成后，用断言更新 `eval_metadata.json` 文件和 `evals/evals.json`。同时向用户解释他们将在查看器中看到什么——包括定性的输出和定量的基准测试。

### 步骤 3：运行完成时，记录计时数据

每个子代理任务完成时，你会收到一条包含 `total_tokens` 和 `duration_ms` 的通知。立即把这些数据保存到运行目录中的 `timing.json`：

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

这是捕获这些数据的唯一机会——它们来自任务通知，不会在其他地方持久保存。在每条通知到达时就处理它，而不是尝试批量处理。

### 步骤 4：评分、汇总并启动查看器

所有运行完成后：

1. **为每次运行评分**——启动一个评分子代理（或在当前会话内评分），读取 `agents/grader.md` 并根据输出评估每个断言。把结果保存到每个运行目录中的 `grading.json`。grading.json 的 expectations 数组必须使用 `text`、`passed` 和 `evidence` 这几个字段（而不是 `name`/`met`/`details` 或其他变体）——查看器依赖这些确切的字段名。对于可以通过程序检查的断言，编写并运行脚本，而不是目测——脚本更快、更可靠，并且可以在多次迭代中复用。

2. **汇总为基准测试**——从 skill-creator 目录运行汇总脚本：
   ```bash
   python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
   ```
   这会生成 `benchmark.json` 和 `benchmark.md`，其中包含每种配置的 pass_rate、时间和 token，以均值 ± 标准差以及差值的形式呈现。如果手动生成 benchmark.json，请参见 `references/schemas.md` 了解查看器所期望的确切 schema。
把每个带技能的版本放在其对应的基线版本之前。

3. **进行分析师环节**——阅读基准测试数据，找出汇总统计数据可能掩盖的模式。关于需要关注的内容，参见 `agents/analyzer.md`（"Analyzing Benchmark Results"一节）——例如无论是否使用技能都始终通过的断言（无区分度）、高方差的评估（可能不稳定），以及时间/token 的权衡。

4. **启动查看器**，同时展示定性输出和定量数据：
   ```bash
   nohup python <skill-creator-path>/eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json \
     > /dev/null 2>&1 &
   VIEWER_PID=$!
   ```
   对于第 2 次及之后的迭代，还要传入 `--previous-workspace <workspace>/iteration-<N-1>`。

   **Cowork / 无头环境：** 如果 `webbrowser.open()` 不可用，或者环境没有显示器，请使用 `--static <output_path>` 来写出一个独立的 HTML 文件，而不是启动服务器。当用户点击"Submit All Reviews"时，反馈会作为 `feedback.json` 文件下载。下载之后，把 `feedback.json` 复制到工作区目录中，供下一次迭代读取。

注意：请使用 generate_review.py 来创建查看器；无需编写自定义 HTML。

5. **告知用户**，大致这样说："我已经在你的浏览器中打开了结果。有两个标签页——'Outputs'让你逐个点击查看每个测试用例并留下反馈，'Benchmark'显示定量对比。完成后，回到这里告诉我一声。"

### 用户在查看器中看到什么

"Outputs"标签页一次显示一个测试用例：
- **Prompt**：给出的任务
- **Output**：技能生成的文件，尽可能内联渲染
- **Previous Output**（第 2 次及之后的迭代）：折叠的部分，显示上一次迭代的输出
- **Formal Grades**（如果运行了评分）：折叠的部分，显示断言的通过/失败
- **Feedback**：一个会在输入时自动保存的文本框
- **Previous Feedback**（第 2 次及之后的迭代）：他们上一次的评论，显示在文本框下方

"Benchmark"标签页显示统计摘要：每种配置的通过率、计时和 token 用量，以及每个评估的细分和分析师的观察结果。

通过上一个/下一个按钮或方向键进行导航。完成后，他们点击"Submit All Reviews"，会把所有反馈保存到 `feedback.json`。

### 步骤 5：阅读反馈

当用户告诉你他们完成了，读取 `feedback.json`：

```json
{
  "reviews": [
    {"run_id": "eval-0-with_skill", "feedback": "the chart is missing axis labels", "timestamp": "..."},
    {"run_id": "eval-1-with_skill", "feedback": "", "timestamp": "..."},
    {"run_id": "eval-2-with_skill", "feedback": "perfect, love this", "timestamp": "..."}
  ],
  "status": "complete"
}
```

空反馈意味着用户认为没问题。把改进的重点放在用户有具体抱怨的测试用例上。

用完查看器后，请终止查看器服务器：

```bash
kill $VIEWER_PID 2>/dev/null
```

## 改进技能

这是整个循环的核心。你已经运行了测试用例，用户已经审阅了结果，现在你需要根据他们的反馈让技能变得更好。

### 如何思考改进

1. **从反馈中进行概括。** 这里发生的大局是：我们正在努力创建可以在众多不同提示词下被使用一百万次（也许是字面意义上的，甚至可能更多，谁知道呢）的技能。在这里，你和用户只是在少数几个示例上反复迭代，因为这样能更快推进。用户对这些示例了如指掌，评估新的输出很快。但如果你和用户共同开发的技能只对这些示例有效，那它就毫无用处。与其做出琐碎的、过拟合的改动，或施加压迫性的限制性"必须"，不如在遇到顽固的问题时，尝试拓展思路，使用不同的比喻，或推荐不同的工作模式。尝试的成本相对较低，也许你会找到绝妙的方案。

2. **保持提示词精简。** 删除那些没有发挥作用的内容。务必阅读转录记录，而不仅仅是最终输出——如果看起来技能让模型浪费了大量时间去做无益的事情，你可以尝试删掉导致这种情况的技能部分，看看会发生什么。

3. **解释原因。** 努力解释你要求模型做的每件事背后的**原因**。如今的大语言模型是*聪明的*。它们有良好的心智理论，在合适的运行框架下，可以超越死板的指令，真正把事情做成。即使用户的反馈简短或带有沮丧情绪，也要努力真正理解任务，以及用户为什么这样写、他们究竟写了什么，然后把这种理解传达到指令中。如果你发现自己在用全大写写 ALWAYS 或 NEVER，或者使用超级僵化的结构，这是一个黄色警示信号——如果可能，请重新组织措辞并解释理由，让模型理解你所要求的事情为何重要。这是一种更人性化、更强大、更有效的方法。

4. **寻找各测试用例之间的重复工作。** 阅读测试运行的转录记录，留意子代理是否都各自独立地编写了类似的辅助脚本，或对某件事采取了相同的多步骤做法。如果 3 个测试用例都导致子代理编写了 `create_docx.py` 或 `build_chart.py`，这就是一个强烈的信号，表明技能应该捆绑该脚本。把它写一次，放到 `scripts/` 中，并告诉技能去使用它。这样可以让未来的每次调用都免于重复造轮子。

这项任务相当重要（我们正在努力每年创造数十亿美元的经济价值！），而你的思考时间并不是瓶颈；请慢慢来，真正地深思熟虑。我建议先写出一份修订草稿，然后重新审视并加以改进。真正尽力设身处地站在用户的角度，理解他们想要什么、需要什么。

### 迭代循环

改进技能之后：

1. 把你的改进应用到技能上
2. 在新的 `iteration-<N+1>/` 目录中重新运行所有测试用例，包括基线运行。如果你正在创建新技能，基线始终是 `without_skill`（没有技能）——这在各次迭代中保持不变。如果你正在改进现有技能，请根据判断选择合理的基线：用户带来的原始版本，或者上一次迭代。
3. 启动审阅器，并使用 `--previous-workspace` 指向上一次迭代
4. 等待用户审阅并告诉你他们完成了
5. 阅读新的反馈，再次改进，重复

一直持续到：
- 用户说他们满意
- 反馈全部为空（一切看起来都很好）
- 你没有取得有意义的进展

## 进阶：盲比较

对于你想要在技能的两个版本之间进行更严格比较的情形（例如，用户问"新版本真的更好吗？"），有一套盲比较系统。详情请阅读 `agents/comparator.md` 和 `agents/analyzer.md`。基本思路是：把两个输出交给一个独立的代理，而不告诉它哪个是哪个，让它判断质量。然后分析获胜者为什么获胜。

这是可选的，需要子代理，大多数用户不需要它。人工审阅循环通常就足够了。

## 描述优化

SKILL.md frontmatter 中的 description 字段是决定 Claude 是否调用某个技能的主要机制。在创建或改进技能之后，主动提出为其优化描述，以提高触发准确率。

### 步骤 1：生成触发评估查询

创建 20 个评估查询——应该触发和不应触发的混合。保存为 JSON：

```json
[
  {"query": "the user prompt", "should_trigger": true},
  {"query": "another prompt", "should_trigger": false}
]
```

这些查询必须是真实的，是 Claude Code 或 Claude.ai 用户实际会输入的内容。不是抽象的请求，而是具体的、细节充分的请求。例如文件路径、关于用户工作或处境的个人背景、列名和取值、公司名称、URL。加上一点背景故事。有些可以是小写的，或包含缩写或拼写错误或口语化的表达。使用不同长度的混合，并侧重于边缘情况，而不是做出泾渭分明的清晰案例（用户将有机会签字确认）。

不好的例子：`"Format this data"`、`"Extract text from PDF"`、`"Create a chart"`

好的例子：`"ok so my boss just sent me this xlsx file (its in my downloads, called something like 'Q4 sales final FINAL v2.xlsx') and she wants me to add a column that shows the profit margin as a percentage. The revenue is in column C and costs are in column D i think"`

对于**应该触发**的查询（8-10 个），要考虑覆盖面。你需要对同一意图使用不同的措辞——有的正式，有的随意。包括用户没有明确点名技能或文件类型，但显然需要它的情形。加入一些不常见的用例，以及这个技能与另一个技能竞争但应该胜出的情形。

对于**不应触发**的查询（8-10 个），最有价值的是近似误判——那些与技能共享关键词或概念，但实际上需要不同东西的查询。考虑相邻领域、朴素的关键词匹配会触发但不应该触发的含糊措辞，以及那些涉及技能所做之事、但处在另一个工具更合适的情境中的情形。

需要避免的关键点：不要让不应触发的查询明显无关。"写一个斐波那契函数"作为 PDF 技能的反面测试太容易了——它什么也测不出来。反面案例应该真正棘手。

### 步骤 2：与用户一起审阅

使用 HTML 模板向用户展示评估集以供审阅：

1. 从 `assets/eval_review.html` 读取模板
2. 替换占位符：
   - `__EVAL_DATA_PLACEHOLDER__` → 评估项的 JSON 数组（不加引号——它是一个 JS 变量赋值）
   - `__SKILL_NAME_PLACEHOLDER__` → 技能的名称
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → 技能当前的描述
3. 写入一个临时文件（例如 `/tmp/eval_review_<skill-name>.html`）并打开它：`open /tmp/eval_review_<skill-name>.html`
4. 用户可以编辑查询、切换是否应该触发、添加/删除条目，然后点击"Export Eval Set"
5. 文件会下载到 `~/Downloads/eval_set.json`——请检查 Downloads 文件夹中最新的版本，以防存在多个（例如 `eval_set (1).json`）

这一步很重要——糟糕的评估查询会导致糟糕的描述。

### 步骤 3：运行优化循环

告诉用户："这需要一些时间——我会在后台运行优化循环，并定期检查进度。"

把评估集保存到工作区，然后在后台运行：

```bash
python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --model <model-id-powering-this-session> \
  --max-iterations 5 \
  --verbose
```

使用系统提示词中的模型 ID（驱动当前会话的那个），这样触发测试就能与用户实际体验到的一致。

在它运行期间，定期查看输出的末尾，向用户更新当前处于哪一次迭代以及分数情况。

它会自动处理完整的优化循环。它把评估集拆分为 60% 的训练集和 40% 的留出测试集，评估当前描述（每个查询运行 3 次以获得可靠的触发率），然后调用 Claude 根据失败的情况提出改进建议。它在训练集和测试集上重新评估每个新描述，最多迭代 5 次。完成后，它会在浏览器中打开一份 HTML 报告，展示每次迭代的结果，并返回带有 `best_description` 的 JSON——该描述是依据测试分数而非训练分数选出的，以避免过拟合。

### 技能触发的工作原理

理解触发机制有助于设计更好的评估查询。技能以名称 + 描述的形式出现在 Claude 的 `available_skills` 列表中，Claude 根据该描述来决定是否查阅某个技能。需要知道的重要一点是，Claude 只会为它自己无法轻易处理的任务查阅技能——像"读取这个 PDF"这样简单的一步查询，即使描述完美匹配也可能不会触发技能，因为 Claude 可以用基本工具直接处理它们。复杂的、多步骤的或专业化的查询在描述匹配时会可靠地触发技能。

这意味着你的评估查询应该足够充实，使 Claude 确实能从查阅技能中受益。像"读取文件 X"这样的简单查询是糟糕的测试用例——无论描述质量如何，它们都不会触发技能。

### 步骤 4：应用结果

从 JSON 输出中取出 `best_description`，并更新技能 SKILL.md 的 frontmatter。向用户展示前后对比并报告分数。

---

### 打包并呈现（仅当 `present_files` 工具可用时）

检查你是否能使用 `present_files` 工具。如果不能，跳过此步骤。如果可以，打包技能并把 .skill 文件呈现给用户：

```bash
python -m scripts.package_skill <path/to/skill-folder>
```

打包之后，引导用户前往生成的 `.skill` 文件路径，以便他们安装它。

## Claude.ai 专用说明

在 Claude.ai 中，核心工作流是相同的（起草 → 测试 → 审阅 → 改进 → 重复），但由于 Claude.ai 没有子代理，一些机制会有所变化。以下是需要调整的地方：

**运行测试用例**：没有子代理意味着无法并行执行。对于每个测试用例，先阅读技能的 SKILL.md，然后按其指令自己完成测试提示词。逐个进行。这不如独立的子代理那样严格（你编写了技能，同时又在运行它，所以你拥有完整的上下文），但这是一次有用的合理性检查——而人工审阅步骤会对此加以弥补。跳过基线运行——只需使用技能按要求完成任务。

**审阅结果**：如果你无法打开浏览器（例如，Claude.ai 的虚拟机没有显示器，或者你在远程服务器上），就完全跳过浏览器审阅器。改为直接在对话中呈现结果。对于每个测试用例，展示提示词和输出。如果输出是用户需要查看的文件（如 .docx 或 .xlsx），把它保存到文件系统，并告诉他们位置，以便他们下载和检查。以内联方式询问反馈："这个看起来怎么样？有什么想改的吗？"

**基准测试**：跳过定量基准测试——它依赖于基线对比，而在没有子代理的情况下这种对比没有意义。专注于用户的定性反馈。

**迭代循环**：与之前相同——改进技能、重新运行测试用例、询问反馈——只是中间没有浏览器审阅器。如果你有文件系统，仍然可以把结果组织到迭代目录中。

**描述优化**：本节需要 `claude` CLI 工具（具体是 `claude -p`），它仅在 Claude Code 中可用。如果你在 Claude.ai 上，请跳过。

**盲比较**：需要子代理。跳过。

**打包**：`package_skill.py` 脚本在任何有 Python 和文件系统的地方都能工作。在 Claude.ai 上，你可以运行它，用户可以下载生成的 `.skill` 文件。

**更新现有技能**：用户可能是在要求你更新一个现有技能，而不是创建新技能。在这种情况下：
- **保留原始名称。** 记下技能的目录名和 `name` frontmatter 字段——原样使用它们。例如，如果已安装的技能是 `research-helper`，则输出 `research-helper.skill`（而不是 `research-helper-v2`）。
- **在编辑前复制到可写位置。** 已安装的技能路径可能是只读的。复制到 `/tmp/skill-name/`，在那里编辑，并从副本打包。
- **如果手动打包，先在 `/tmp/` 中暂存**，然后复制到输出目录——直接写入可能因权限而失败。

## Cowork 专用说明

如果你在 Cowork 中，需要了解的主要事项是：

- 你拥有子代理，因此主要工作流（并行启动测试用例、运行基线、评分等）都能正常工作。（不过，如果你遇到严重的超时问题，改为串行而非并行运行测试提示词也是可以的。）
- 你没有浏览器或显示器，所以在生成评估查看器时，请使用 `--static <output_path>` 来写出一个独立的 HTML 文件，而不是启动服务器。然后提供一个链接，供用户点击以在其浏览器中打开该 HTML。
- 出于某种原因，Cowork 的设置似乎使 Claude 不太倾向于在运行测试之后生成评估查看器，所以再重申一次：无论你是在 Cowork 还是在 Claude Code 中，运行测试之后，你都应该始终先生成评估查看器，让人类在你自己修改技能并尝试做出更正之前先查看这些示例，使用 `generate_review.py`（而不是自己编写独特的 html 代码）。提前说声抱歉，但我要用全大写了：在你自己评估输入之前，先生成评估查看器！你要尽快把它们摆到人类面前！
- 反馈的工作方式有所不同：由于没有运行中的服务器，查看器的"Submit All Reviews"按钮会把 `feedback.json` 作为文件下载。然后你可以从那里读取它（你可能需要先请求访问权限）。
- 打包可以正常工作——`package_skill.py` 只需要 Python 和文件系统。
- 描述优化（`run_loop.py` / `run_eval.py`）在 Cowork 中应该能正常工作，因为它通过子进程使用 `claude -p`，而不是浏览器，但请等到你完全完成技能的制作并且用户同意它状态良好之后再进行。
- **更新现有技能**：用户可能是在要求你更新一个现有技能，而不是创建新技能。请遵循上面 claude.ai 部分中的更新指引。
