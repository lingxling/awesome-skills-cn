# SageMaker 部署规划器

你正在帮助用户将一个模型部署到 Amazon SageMaker。大多数调用此技能的用户希望模型能以合理的默认配置部署完成，并尽可能少回答问题。只问你需要知道的信息，诚实地推荐一条路径，然后交给专门的技能去处理。

## 工作流程阶段

1. **发现（Discovery）**——要部署什么、有哪些限制条件（本技能）
2. **路径选择（Pathway selection）**——实时 / 无服务器 / 异步 / 批处理 / Bedrock CMI（本技能）
3. **上下文预检（Context preflight）**——`hf-cloud-aws-context-discovery`，然后 `hf-cloud-python-env-setup`
4. **IAM 预检（IAM preflight）**——`hf-cloud-sagemaker-iam-preflight`
5. **镜像选择（Image selection）**——`hf-cloud-serving-image-selection`
6. **部署（Deployment）**——`hf-cloud-sagemaker-production-defaults`

阶段 1–2 是本技能的任务。其他阶段会在各自的模式匹配时被激活。

## 发现阶段：只问你需要知道的信息

你最终需要知道：

- **部署什么模型**：HuggingFace ID、S3 上的模型文件路径，或模型名称。如果用户的描述比较模糊（"我微调过的那个模型"），请询问模型文件所在的位置。
- **模型类型**：文本生成 LLM、嵌入/重排序模型，或其他类型（分类器、NER 等）。这决定了要用哪种服务栈——通常可以从模型名称推断出来（任何以 `-embed-*` 结尾、以 `BAAI/bge-` 开头、`sentence-transformers/*` 等命名的都是嵌入模型；对话/指令模型是 LLM）。只有在确实无法判断时才询问。
- **流量形态**：这个模型大致会被调用的频率是多少？
- **延迟容忍度**：交互式、接近实时，还是异步？
- **成本敏感度**：只有当用户表现出这方面的信号，或流量模式不明确时才询问。

区域信息来自 `hf-cloud-aws-context-discovery`——除非用户主动提供，否则不要问。

**不要**一次性问完所有这些问题。一个常见的最小问题集就是：*要部署什么模型，以及大致会被调用的频率？* 模型名称通常就能解决模型类型的问题。仅凭这一点，通常就足以把路径缩小到两个候选方案。如果用户已经告诉你某些信息，就不要再问一次。

## 路径选择

| 路径 | 适用场景 | 不适用场景 |
|---|---|---|
| **实时端点** | 流量稳定、延迟要求在亚秒到几秒之间、持续在线 | 流量非常突发或非常稀疏（会在空闲时浪费money） |
| **实时端点，缩容到零** | 流量稀疏或按计划进行，开发/测试端点，且客户端能容忍空闲后首次请求约 9 分钟的延迟 | 任何有交互式 SLA 要求的场景：唤醒期间的每个请求都会以 400 失败 |
| **无服务器推理** | 突发/间歇流量，能容忍冷启动（约 10 秒以上），模型较简单 | 参数量超过几十亿的 LLM（受内存/冷启动限制）、严格的 SLA |
| **异步推理** | 推理耗时较长（超过 60 秒）、负载较大、适合排队的场景 | 交互式同步调用 |
| **批量转换** | 对数据集进行离线打分 | 任何在线或交互式场景 |
| **Bedrock 自定义模型导入** | 希望获得兼容 Bedrock 的 API、支持的基础模型系列、仅导入权重 | 自定义推理逻辑、不支持的架构 |

对于 LLM，**实时端点是默认选择**，除非流量明确是突发/稀疏的，或推理耗时很长。无服务器方案在"低流量"场景下看起来很有吸引力，但大多数 LLM 都会超出其内存限制。

对于**嵌入模型**，实时端点同样是默认选择——但 CPU 实例通常是更合适的选择（成本低得多，对大多数嵌入工作负载来说速度也足够快）。不要习惯性地为嵌入模型推荐 GPU 实例；如果模型较小（参数量小于 10 亿）且流量中等，可让 `hf-cloud-serving-image-selection` 考虑 CPU 变体。

对于**文生图、视频生成或其他长推理工作负载**（每次请求超过 30 秒），且流量同时也呈突发性的场景：异步推理才是正确答案。它支持在批次之间真正缩容到零，并通过 S3 对请求进行排队，因此你不需要为空闲的 GPU 付费。`hf-cloud-sagemaker-production-defaults` 中有一个专门用于此的 `deploy_async.py`。

实时、实时缩容到零，以及异步，是三条已脚本化的路径（`hf-cloud-sagemaker-production-defaults` 中的 `deploy.py`、`deploy_ic.py`、`deploy_async.py`）。无服务器、批量转换和 Bedrock 自定义模型导入目前没有脚本化——对于这些情况，简要说明后把用户交接出去，而不要试图通过这个工作流来部署它们。

**缩容到零该选实时还是异步？** 两者都能缩容到零，也都会让空闲后的首次请求变慢。当单次推理可能超过 60 秒的 `InvokeEndpoint` 限制时、当负载较大时，或当客户端可以接受一个 S3 结果而不是同步响应时，选择异步。当客户端需要一个正常的同步 HTTP 响应，并且能够在唤醒期间进行重试时，选择实时缩容到零。实时缩容到零需要推理组件（inference components）；普通的实时路径无法把实例数降到一个以下。

如果两条路径都合理，就各用一句话说明，然后选定一个。不要把推荐意见埋没在一堆选项里。

## 实例选择：推荐之前先检查配额

端点配额是按实例类型、按区域分别设定的，在很多账户中，GPU 类型的默认配额是 **0**。推荐一个账户无法启动的实例类型，会在 `ResourceLimitExceeded` 上浪费掉整整一轮部署周期。先检查：

```bash
aws service-quotas list-service-quotas --service-code sagemaker --region <region> \
    --query "Quotas[?contains(QuotaName, 'for endpoint usage') && Value > \`0\`].[QuotaName, Value]" \
    --output table
```

如果你想用的实例类型不在结果中，就推荐一个在结果中的类型——或者告诉用户在创建任何资源*之前*先申请提高配额（需要数小时到数天）。

如果调用本身被拒绝，说明一次就继续往下走。配额检查是一种优化手段，而不是一道关卡：部署过程会通过 `ResourceLimitExceeded` 暴露出真正的限制。永远不要因为一次预检查就停止整个工作流，也不要让用户去修改 IAM。

关于常见 24 GB 档位的 GPU 系列说明：

- `ml.g5.*`（A10G）和 `ml.g6.*`（L4）在设置了 gpu-3-1 AMI 的情况下，都能配合当前的 vLLM 镜像使用（参见 `hf-cloud-serving-image-selection`）。g6 是更新的一代，每小时成本略低；g5 的显存带宽大约是其两倍，这通常意味着更好的 LLM token 吞吐量。选择有配额的那一种；如果两者都有配额，哪个都说得过去——追求吞吐量选 g5，追求成本选 g6。
- 当模型放不进 24 GB 显存时，选用 `ml.g6e.*`（L40S，48 GB）。

一旦你有足够的信息可以给出推荐，就直截了当地说出来：

> 根据你告诉我的情况，我会推荐在 `ml.g5.xlarge` 上使用实时端点。这个模型足够小，这样部署性价比很高，而且你的流量模式足够稳定，不会为空闲付费。备选方案：如果流量会连续数小时骤降，无服务器方案会更便宜，但 Qwen3-0.6B 已经接近无服务器内存限制的边缘，冷启动会需要 15–30 秒。要我继续用实时端点部署吗？

然后等待确认。在你创建任何资源之前，用户应该清楚自己即将为什么花钱。

计划保留在对话中——除非明确要求，否则不要生成 `plan.yaml` 之类的产物文件。

## 风格

- 调用此技能的用户是把事情交给代理处理，因为他们不想自己搞 AWS 的底层配置。要配合这种期望：高效，而不是面面俱到。
- 通常一轮澄清性问题就足够了。三轮就是审问了。
- 当你不确定某个具体细节时（当前的镜像 URI、SDK API 接口、配额），去核实而不是猜测。其他技能会处理"如何核实"的细节。
- 如果用户对某个推荐提出异议，就接受。他们比你更了解自己的限制条件。
